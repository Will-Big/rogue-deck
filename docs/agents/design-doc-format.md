# 설계·계획 문서 골격

**언제 읽나:** 새 설계 문서나 실행 계획을 쓰기 전에, 그리고 기존 설계에 위험·질문을 제기하기 전에.
AGENTS.md 규칙 28·29·33이 이 문서를 가리키며, 규칙에는 판단 기준만 남기고 골격은 여기 있다.

지금까지 문서의 주 목적이 세션 인계였던 탓에 사람이 읽기에 정보량이 과했고, 대충 읽고 넘어간 구조
결정이 나중에 리팩터링으로 돌아왔다 — SO 저작에서 JSON으로, 코드 조합형 카드에서 데이터 교체형으로,
고정형 개입 카드에서 확장형으로 세 번 겪었다. 그래서 독자를 갈랐다.

## 두 독자는 파일도 형식도 다르다

2026-08-30 결정, 이 날짜 이후 새 문서부터 적용한다.

| | 사람 검수용 | 세션 인계용 |
|---|---|---|
| 파일 | `<이름>.html` | `<이름>.md` |
| 형식 | HTML + 인라인 SVG 다이어그램 | Markdown |
| 기준 | 이것만 보고 구조를 승인할 수 있는가 | 이것만 읽고 구현할 수 있는가 |

`.md`는 머리말에서 짝이 되는 `.html`을 링크하고 `## 상세`만 담는다.

## `.html`에 담을 것

아래 항목을 순서대로 담되 분량 제한이 없다 — 판단 기준은 줄 수가 아니라 "이것만 보고 승인이
되는가"다.

- **무엇을 만드나** — 2~3문장
- **구조** — 등장 객체 3~7개. 객체 / 책임(한 줄) / 이 객체가 모르는 것
- **의존 방향** — **다이어그램으로 그린다.** 화살표에 관계를 적는다("id로 뷰 조회" 같은)
- **확장 축** — 런타임에 갈아끼울 수 있는 것 / 한번 정하면 고정되는 것
- **대안과 기각 이유** — 갈림길 1~2개. **채택안과 기각안의 차이를 그림으로** 나란히 보인다
- **이 선택으로 나중에 어려워지는 것** — "없다"라고 쓰지 않는다
- **실행 예시** — 대표 상황 하나를, 어떤 객체가 어떤 매개변수 값으로 수행하는지 끝까지 따라간다

## 다이어그램 규칙

이름이 아니라 **작동 방식**을 그린다. 상자에 이름만 적은 그림은 산문보다 정보가 적다. 화살표에
라벨을 붙이고, 대안 비교는 **차이가 보이게** 나란히 놓는다. 문장으로 더 빠르면 문장을 쓴다 —
장식용 그림은 넣지 않는다. 자체 완결 인라인 SVG만 쓰고 외부 이미지·스크립트·라이브러리를
참조하지 않는다.

## 쓰지 않는 것, 비울 수 없는 것

- **실행 예시에 한해 구체적 값을 쓴다.** 대표 상황 하나를 골라 입력값·객체·호출 순서·최종 결과를
  값과 함께 따라간다. 구조가 맞는지는 추상 설명이 아니라 한 번의 구체적 실행에서 드러난다.
- 그 밖의 절에는 알고리즘 설명을 넣지 않는다. "어떤 로직인가"가 아니라 "무엇이 무엇에
  의존하는가"만 쓴다.
- **마지막 세 항목은 비워 둘 수 없다.** SO의 런타임 생성 한계처럼, 알고 있었어야 할 제약이
  사용자에게 전달되지 않는 지점이 정확히 그 칸이다.
- **한 객체의 책임을 '그리고' 없이 한 줄로 못 쓰면** 쪼갤 후보다(규칙 30). 쪼개지 않기로 했다면
  이유를 개요 절에 적는다. "이 객체가 모르는 것" 칸이 비면 그것은 전부 아는 객체이니 경고로 본다.
- **의존 화살표가 한 객체로 몰리면** 그 사실을 개요 절에 적고 사용자 판단을 받는다. 중앙 관리자가
  필요해서 몰린 것인지, 거기가 편해서 몰린 것인지는 사람이 정한다.
- **미래 기능과의 접점은 쓰지 않는다.** 아직 없는 기능을 걱정해 지금 구조를 비트는 것은
  리팩터링의 근거가 아니다. 마찰은 실제로 부딪혔을 때, 또는 확장성 부족이 확인됐을 때 잡는다.

## 개요로 승인받고, 상세로 구현한다 (규칙 29)

- 문서를 참조할 때 **실행 근거는 `.md`의 `## 상세`에서만** 얻는다. `.html` 개요는 방향 확인용이며,
  개요만 보고 구현에 들어가지 않는다.
- 새 스펙·계획을 만들면 **`.html` 개요를 제시해 승인받은 뒤** 상세를 실행한다. 상세 전문을 붙여
  승인을 요청하지 않는다.
- **개요와 상세가 어긋나면 상세를 따르지 않고 멈추고 묻는다.** 불일치는 문서 오류가 아니라 설계
  오류 신호다.
- **기존 문서는 소급해 고치지 않는다.** 그 문서를 수정할 일이 생겼을 때 이 골격으로 맞춘다.

## 확정된 결정은 원칙 문장으로 적는다

- 계획·설계 문서의 확정된 요구는 결론만이 아니라 **그 결론을 낳은 원칙을 일반 문장으로** 적는다.
  표와 예시는 원칙을 가리키는 자리이며, 정의를 표 셀에만 두지 않는다. 셀은 요약이라 다르게 읽힌다.
- 사용자가 범주·용어를 정의하면 **요약하지 않고 그 말 그대로** 옮긴다. 요약하는 순간 정의의 핵심이
  빠질 수 있다.
- 원칙에 걸리는 경계 사례(예: 수치가 의미 없는 상태)는 원칙 바로 옆에 적는다.

## 규칙 33 — 설계에 위험·질문을 제기하기 전에 기존 결정에 대 본다

2026-10-14 한 세션에서 같은 실패가 두 번 났다.

- 상태 수치를 `Stacks` 하나로 합치는 계획(F10-1)을 두고 AI가 "수치가 둘 필요한 상태가 나오면
  재작업이 생긴다"는 위험을 제기했다. 같은 답에서 단계 1.1의 "확정된 사용자 요구: … 독립 기간 없음.
  이 요구를 다시 후보로 올리지 않는다"를 직접 인용했는데도 그랬다. 결정은 문서에 있었고, 위험을
  떠올린 순간 거기에 대 보지 않은 것이다.
- 이어서 수치 해석 표의 '존재형 효과' 행을 "누적 수치를 갖는다" 열만 보고 수치가 의미 있는 상태로
  읽어, 이미 답이 정해진 검토 항목을 계획에 더했다. 사용자의 정의는 "관련 상태 로직이 on/off로만
  동작하고 누적 수치는 영향을 끼치지 않는 상태"였다.

두 번 다 원인은 문서에 결정이 없었던 것이 아니라 **질문을 만든 쪽이 결정을 확인하지 않은 것**이다.
문서 보강(위 절)만으로는 막히지 않는다 — 막혀야 할 지점은 위험을 떠올린 순간이다. "항상 확인해라"는
지시가 몇 턴 만에 감쇠한다는 규칙 31의 교훈대로, 확인을 지시가 아니라 답의 형식으로 강제한다.

- 위험·질문에는 대 본 결정의 경로와, 그 결정이 이 경우를 다루지 않는 이유 한 줄을 붙인다.
- 대 보지 않았으면 '기존 결정 미확인'이라고 문장에 적는다. 표시 없는 질문은 확인을 거친 것으로 본다.
- 확인했더니 결정이 이미 답하고 있으면 질문을 꺼내지 않고 그 결정을 인용한다.
