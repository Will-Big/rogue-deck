카드·상태 변경 — 주 목표와 단계별 계획

2026-10-08 · Markdown 상세

현재 설계 검토 중입니다. 후속 단계는 개요이며, 해당 단계에 착수할 때 상세를 작성합니다.

주 목표계획을 검토하는 방법큰 계획 1 — 상태 수치와 수명 처리 통일큰 계획 2 — 중앙 상태 규칙의 변경과 설명 연결큰 계획 3 — 카드의 런 변경과 전투 변경 완성전체 계획에 유지하는 요구‘이름 중복 정리’의 의미와 처리실행 예시 — 전체 목표의 확인 기준실행 경계

주 목표

  • 카드·상태 규칙을 게임 중 변경할 수 있고, 실제 동작과 설명이 같은 변경 결과를 보여준다.
  • 런 동안 유지되는 변경과 전투 동안만 유지되는 변경을 구분한다.
  • 상태 인스턴스의 수치는 Stacks 하나로 통일하고, 같은 상태를 다시 받으면 합산한다.

계획을 검토하는 방법

  • 이 문서는 큰 계획의 목적·순서와 작은 단계의 검토 단위만 정한다.
  • 현재 검토 단계는 1.1 상태 수치의 저장 위치와 해석 책임이다. 현재 단계의 상세 / HTML 설계도.
  • 다음 단계는 착수할 때 상세를 작성한다. 미래 단계의 객체 이름·메서드·작업 파일·테스트 코드를 지금 확정하지 않는다.
  • 단계마다 설계 검토 → 해당 단계의 구현 계획 작성 → 구현·검증 → 결과 검토로 진행한다. 현재는 설계 검토 중이며 제품 구현을 시작하지 않는다.
  • 큰 계획은 따로 검토·구현할 수 있다. 하나의 거대한 변경이나 커밋으로 묶을 필요가 없다.

큰 계획 1 — 상태 수치와 수명 처리 통일

  • 목적: 상태별 숫자의 의미는 유지하면서 저장·합산·감소·제거 계약을 일관되게 만든다.
  • 먼저 하는 이유: 현재 인스턴스에는 Count·Magnitude·VisitsLeft가 있고, Add의 갱신과 Stack의 합산이 나뉜다. 이후 변경 기능이 사용할 수치 계약부터 정한다.
  • 근거: StatusInstance.cs:11, StatusBag.cs:16, StatusBag.cs:78.

큰 계획 2 — 중앙 상태 규칙의 변경과 설명 연결

  • 목적: 정도·성장량·배율 같은 공통 규칙을 런/전투 기간과 파티/개인 범위에 맞게 변경한다.
  • 순서의 이유: 계획 1에서 정한 개인 Stacks와 중앙 규칙의 경계를 사용한다. 카드 변경 전체를 먼저 구현할 필요는 없다.
  • 현재 근거: 둔화 행동은 중앙 콘텐츠의 정도를 읽는다(SlowBehavior.cs:15). 이후 저장 방식은 아직 설계하지 않는다.

큰 계획 3 — 카드의 런 변경과 전투 변경 완성

  • 목적: 소유 카드의 영구 변경과 임시 변경을 구분하고 실행·설명에 같은 유효 카드를 사용한다.
  • 계획 2의 상태 규칙 변경과 연결하는 부분은 해당 단계에 착수할 때 설계한다. 기존 카드 구조의 재사용 범위도 그때 코드로 확인한다.

전체 계획에 유지하는 요구

  • 설명에서 수치 개념을 count라고 부를 수 있지만 실제 구현 필드명은 Stacks다.
  • 같은 키의 인스턴스·심볼은 하나이며 수치만 합산한다. 갱신/교체와 부여별 기록은 만들지 않는다.
  • Count·Magnitude·VisitsLeft를 Stacks로 통합한다. 방어량과 독립된 N턴 만료는 지원하지 않는다.
  • 상태 부여자를 추적하지 않고 Stacks만큼 N회 반복 실행하지 않는다.
  • 범용 효과는 플레이어 파티 전체에 적용하고 적은 제외한다. 별도 UI 여부는 아직 결정하지 않는다.
  • 호버는 현재 count를 문장에 삽입하지 않는다. 중앙 규칙 값이 바뀌면 해당 설명도 바뀐다. 카드의 상태 부여량 문구는 유지한다.
  • 코드의 상태 행동이 수치의 의미를 해석한다. JSON에 중첩 실행 알고리즘을 넣지 않는다.
  • 다국어·새 능력 콘텐츠·범용 스크립트 엔진·무관한 리팩터링은 범위 밖이다.

‘이름 중복 정리’의 의미와 처리

  • 상태끼리 같은 이름이라는 뜻이 아니라 이름 데이터의 이중 보관을 뜻했다.
  • 콘텐츠가 이름을 조회한다(StatusContentCatalog.cs:55). 설명 카탈로그가 그 이름을 다시 등록한다(KoreanDescriptionCatalog.cs:46). 등록된 이름은 별도 사전에 보관된다(StatusDescriptionRegistry.cs:9).
  • 이 사실만으로 즉시 삭제해야 하는 오류라고 판단하지 않는다. 별도의 필수 단계에서 제외한다.
  • 2.4의 설명 조회 경로를 검토할 때 직접 콘텐츠를 조회하는 편이 단순한지 판단한다. 필요하다면 그 단계의 작은 정리로 포함한다.

실행 예시 — 전체 목표의 확인 기준

  • 둔화: 중앙 정도 +2, 개인 count 3에 둔화 3을 더하면 count 6. 실행 순서 변화는 +2를 유지한다. 기간 감소 후 count 5가 되어도 호버 문구는 같다.
  • 규칙 변경: 파티 둔화 정도를 전투 동안 +3으로 바꾸면 파티의 동작·호버는 +3을 사용한다. 개인 count와 적의 정도는 이 변경으로 바뀌지 않는다.
  • 카드 변경: 원본 피해 3에 런 변경 +2, 전투 변경 +4가 더해지면 피해 9. 전투 종료 후 5, 새 런에서는 원본 3이다.

실행 경계

  • 현재 단계 상세만 검토 근거다. 후속 개요만 보고 구현하지 않는다.
  • 제품 코드는 전용 워크트리에서 구현한다. 새 규칙에는 헤드리스 테스트를 작성하고 Tools/verify.sh 전체를 통과시킨다.
  • master 머지는 별도 사용자 승인 후 진행한다.
