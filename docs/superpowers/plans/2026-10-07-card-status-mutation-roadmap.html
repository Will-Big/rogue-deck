카드·상태 변경과 설명 일치 — 작업 계획

2026-10-07 · Markdown 상세

설계 논의 중. 작업 순서는 합의했고, 상태 변경의 적용 범위는 추가 논의한다. 이 문서는 단계별 로드맵이며, 구현을 시작하는 승인 문서가 아니다. 카드·상태별 구현 계획은 첫 단계의 결정 후 작성한다.

무엇을 만드나

  • 전투 중 카드·상태의 수치, 지속 기간, 적용·소모 방식이 바뀌고 설명도 그 결과를 표시한다. 카드는 대상 변경과 추가 효과도 지원한다.
  • 런 변경은 다음 전투에도 유지하고, 전투 변경만 전투 경계에서 제거한다. 다국어와 무관한 추상화 정리는 보류한다.

작업 순서

단계우선순위 / 종류끝났다고 판단하는 기준
A. 적용 범위·기간 결정P0 / 설계공통·부여자·보유자 중 지원 범위, 기존 상태의 처리, 실행선 카드 변경 시점이 문서로 확정된다.
B. 카드 변경P1 / 기능 구현원본 + 런 변경 + 전투 변경이 실행과 설명에 반영되고, 다음 전투에는 런 변경만 남는다.
C. 상태 변경P1 / 기능 구현합의한 범위에서 변경된 규칙을 행동과 부여가 읽고, 전투·런 사이에 값이 섞이지 않는다.
D. 설명·표시 연결P1 / B·C에 포함변경 직후 설명과 실제 효과가 같고 현재 상태의 남은 기간도 정확하다.
E. 이름 중복 제거P2 / 구조 정리이름의 별도 복사 없이 기존 설명과 로그를 유지한다.

구조

상태 변경 저장 위치는 단계 A에서 확정한다. 아래는 책임의 분리이며 모든 항목이 새 클래스가 된다는 뜻은 아니다.

객체 / 역할책임모르는 것
원본 콘텐츠카드·상태의 저작 기준값 제공현재 런과 전투의 변경
OwnedCard한 소유 카드의 유효 정의 제공한국어 문장과 화면 배치

상태 행동 / 효과 핸들러유효 규칙에 따른 게임 동작 수행변경 목록의 저장·화면 배치

의존 방향

확장 축

  • 런타임 변경: 지원하기로 한 수치·지속·정책, 카드의 대상·효과 목록.
  • 고정: 원본 불변, 변경 기간의 의미, 기존 핸들러 등록 방식. 새 행동 종류는 코드 핸들러로 추가한다.
  • 카드와 상태는 별도 데이터 타입으로 구현한다. 공통 원칙만으로 범용 변경 엔진을 만들지 않는다.

대안과 기각 이유

  • 설명에서 변경을 다시 계산하는 방법은 채택하지 않는다. 실행과 표시가 별도 합성 경로를 가지면 같은 변경을 다르게 해석할 수 있다.
  • 공통·부여자·보유자 중 어느 상태 변경 범위를 택할지는 아직 기각하거나 채택하지 않았다. 실제 효과 예시를 기준으로 논의한다.

이 선택으로 나중에 어려워지는 것

  • 런과 전투가 같은 소유 카드를 참조하므로, 전투 경계에서 임시 변경을 제거하는 경로를 빠뜨리면 변경이 남는다. 정상 종료와 다음 진입 양쪽에서 검증한다.
  • 미해결 카드의 변경을 반영하려면 카드 실행 데이터·비용·순서의 갱신 시점을 맞춰야 한다. 이 규칙은 구현 전에 확정한다.
  • 부여자별 상태 변경을 지원하면 강화된 독의 재부여·합산·전이 시 어느 규칙을 보존할지 결정해야 한다. 지금 단순히 ‘특정 대상 지원’으로 묶으면 숨은 규칙이 생긴다.

실행 예시

아래는 기존 카드 설계의 합성 순서를 검증하는 테스트 예시다. 새 밸런스 콘텐츠를 추가하는 결정은 아니다.

  1. 원본 카드의 피해는 3이다. 소유 카드 A와 B가 같은 원본을 사용한다.
  2. A에 런 변경 ‘피해 +2’, 전투 변경 ‘피해 +4’를 등록한다.
  3. A의 유효 카드는 피해 9다. 실행은 9를 사용하고 설명은 변경 후 효과 데이터에서 9를 표시한다. B는 3이다.
  4. 전투 종료 시 A의 전투 변경만 지운다. 다음 전투에서 A의 피해와 설명은 5이고 B는 3이다.
  5. 새 런은 새 소유 카드로 시작한다. 원본과 공유 콘텐츠에 변경을 쓰지 않았으므로 피해 3이다.

논의할 상태 변경의 세 의미

범위예시추가 결정
공통 규칙이 전투의 모든 독은 성장량 +1파티와 적 양쪽에 적용되는가?
부여자별A가 부여한 독만 성장량 +1B가 추가로 독을 부여하거나 전이하면 강화가 남는가?
보유자별B에게 붙은 독만 성장량 +1누가 부여했는지와 무관하게 B에게만 적용되는가?

먼저 실제로 원하는 강화 예시를 고른 뒤 지원 범위를 결정한다. 모든 범위를 지원하는 공통 구조를 먼저 구현하지 않는다.
