# 카드·상태 변경과 중첩 실행 구조 — 설계 후보와 작업 계획

사람 검토용: [HTML 설계도](2026-10-07-card-status-mutation-roadmap.html)

## 상세

### 1. 이번 개정의 기준

- 개정일: 2026-10-08. 문서 상태: 구조 후보 검토 중. 아래 새 타입·API·규칙은 구현 사실이 아닌 설계 제안이다.
- 사용자가 요구한 ‘모르는 것’ 열과 ‘이 선택으로 나중에 어려워지는 것’ 절을 제거했다. 구조 설명은 상속·보관·호출 관계와 실행 순서를 중심으로 한다.
- 모든 상태는 재부여와 중첩 저장을 지원한다. 요새화의 ‘쌓일 수 없음’은 재부여 거부가 아니라 **여러 번 얻어도 규칙 변경은 한 번만 유효함**으로 해석한다.
- 중첩 수, 한 번의 효과 수치, 남은 지속 기간을 서로 다른 값으로 다룬다. 가속·둔화도 정도와 지속 기간을 동시에 표현한다.
- 분노 2는 힘 +1 효과를 두 번, 독의 대가 2는 독 1 부여를 두 번 실행한다. 힘 +2 / 독 2 한 번으로 최적화하지 않는다.
- 중첩의 의미와 실행 알고리즘은 상태 행동 코드가 정한다. JSON에는 콘텐츠 수치·기간·적용 대상 등 데이터만 저작한다. 반복 루프·실행 횟수 수식·중첩 정책 판별자를 추가하지 않는다.
- 상태의 행동은 파티와 적에게 같은 규칙으로 적용한다. 부여자의 정체에 따라 숨은 상태 규칙을 달리하지 않는다.
- 범용 효과(요새화·독 성장량 변경)와 개별 효과(특정 캐릭터의 방어 획득량 증가)를 실행 데이터와 표시 데이터에서 구분한다.
- **확정:** 범용 효과 카드를 사용하면 플레이어 파티 전체에 적용한다. 적은 포함하지 않는다. UI를 기존 상태 영역에 함께 표시할지 별도 영역에 표시할지는 미결정이다. 이번 계획에는 표시 데이터의 구분을 포함하고 별도 UI 신설을 확정하지 않는다.
- 원본 + 런 변경 + 전투 변경, 실행·설명의 동일 데이터 사용, 카드 대상·추가 효과 변경, 다국어 후순위라는 기존 요구는 유지한다.
- 제품 코드 구현은 이번 작업에 포함하지 않는다. 후보 선택 후 해당 설계의 구체 구현 계획을 작성한다. 기존 기준 문서는 후보 검토만으로 대체하지 않는다.

### 3. 추천 순서의 구조 후보

| 순위 | 후보 | 저장 형태 | 중첩 해석 | 장점 | 단점 |
|---|---|---|---|---|---|
| 1 | 부여 기록 보관 + 상태별 행동 + 공통 실행 경계 | 상태 키별 묶음 안에 각 부여의 수치·중첩·만료 보관 | 행동이 존재 판정 / 합산 / 반복 계획을 만든다 | 다른 기간·수치 보존, JSON 책임 제한, 기존 핸들러 확장 방식 활용 | 기존 단일 StatusInstance 조회·소모·이벤트 경로를 바꿔야 한다 |
| 2 | 키별 단일 상태 + 중첩 정책 객체 조합 | 키마다 합산 수치·중첩 수·대표 기간 하나 | Presence/Sum/Repeat 정책 객체 | 저장과 조회가 간단하고 동일한 정책을 공유하기 쉽다 | 서로 다른 기간은 최대/갱신/연장 중 하나로 손실된다. 보존하려면 결국 부여 목록이 필요하고 정책 객체 수도 늘어난다 |
| 3 | 부여마다 독립 상태 객체 | 모든 부여를 별도 상태 객체로 저장 | 각 객체가 훅 수행, 존재형은 별도 중복 제거 | 부여별 기간과 효과가 자연스럽게 독립된다 | 표시 묶음·존재형 억제·조회·전이·반응 순서를 별도로 정리해야 한다. 모든 상태를 한 번씩 호출하면 요새화 요구와 충돌한다 |

**추천 근거:** 현재 StatusBag은 이미 키별 조회를 제공한다. 이 조회는 표시 묶음으로 남기고 저장만 부여 기록으로 넓히면, 사용자가 요구한 서로 다른 값과 N회 실행을 함께 표현할 수 있다. 후보 2의 단일 대표 기간은 가속의 다른 기간 부여를 보존하지 못하며, 후보 3의 무조건 객체별 실행은 요새화와 수치 합산까지 횟수로 취급한다. 후보 1도 중앙 switch나 범용 스크립트 엔진을 만들지 않는다.

### 4. JSON에 실행 규칙을 넣지 않는 후보

| 순위 | 방법 | 장점 | 단점 | 판단 |
|---|---|---|---|---|
| 1 | 등록된 상태 행동이 집계·반복 계획 제공 | 기존 StatusBehavior·IReactionHandler 패턴 활용. 상태별 메커니즘에 맞게 구현 | 새 메커니즘은 C# 코드와 테스트가 필요 | 추천. JSON 숫자·기간은 읽되 반복 방식은 코드에서 결정 |
| 2 | 코드 정책 객체를 상태 행동에 조합 | 여러 상태가 완전히 같은 정책일 때 재사용 가능 | 상태별 정책·기간·반응의 조합을 위한 타입이 증가 | 동일한 구현이 실제로 반복될 때만 추출 |
| 3 | 중첩 방식별 행동 상속 계층 | 존재형/합산형/반복형을 클래스 이름으로 식별 가능 | 한 상태가 여러 훅에서 다른 방식을 쓰면 상속 축이 충돌 | 전체 구조의 기본으로는 비추천 |

JSON에 `repeatPerStack`, `stackingMode`, 실행 스크립트 같은 규칙 선택 필드를 두는 후보는 사용자 요구와 맞지 않아 채택하지 않는다. 코드에 게임 메커니즘을 구현하는 것은 등록형 행동의 책임이다. 단, 독 성장량·가속 정도 같은 튜닝 숫자는 JSON 또는 변경 데이터에서 읽으며 코드 상수로 옮기지 않는다.

### 5. 추천안의 객체·상속·참조 관계

| 객체 | 상태 | 역할 | 관계 |
|---|---|---|---|
| CombatState | 기존 수정 | 전투 데이터 보관 | 개체·PartyStatusBag·EffectiveStatusRules 참조 보관 |
| PartyMember / Enemy | 기존 수정 | 개체의 전투 데이터 보관 | 각자 StatusBag과 개별 변경 데이터 보관 |
| StatusBag / PartyStatusBag | 기존 수정 / 새 저장 위치 | 개별·파티 범용 상태 기록 보관 | 동일한 StatusGroup/StatusGrant 모델 사용. 파티 저장 위치는 적의 조회에 포함하지 않음 |
| StatusGroup | 새 데이터 타입 제안 | 같은 키의 부여를 조회·표시용으로 묶음 | List<StatusGrant> 보관, 행동 상속 없음 |
| StatusGrant | StatusInstance 대체 제안 | 한 부여의 중첩 수·값·만료 보관 | GrantId, StackCount, StatusValues, 만료 정보 보관 |
| StatusValues | 새 데이터 기반 타입 제안 | 상태 수치의 타입 표현 | ScalarValues / OrderShiftValues / PresenceValues 등 필요한 데이터만 파생 |
| StatusBehavior | 기존 수정 | 해당 상태의 집계·기본 훅 규칙 제공 | IStatusBehavior 구현 기반 클래스. 구체 행동이 상속 |
| IReactionHandler | 기존 수정 | 사건 반응 조건·관찰 역할·반복 계획 제공 | RageReaction / PoisonMasterReaction 등이 구현 |
| StatusRegistry / ReactionRegistry | 기존 유지·수정 | 키로 행동 찾기 | 행동 객체 참조. 상태 런타임 데이터는 보관하지 않음 |
| EffectExecutor / ReactionDispatcher | 기존 수정 | 효과 경계·반응 호출 순서 조정 | 계산은 핸들러에 위임. 새 총괄 StatusManager는 만들지 않음 |
| EffectiveStatusRules | 새 조회 객체 제안 | 원본과 기간별 규칙 변경의 유효 결과 제공 | 콘텐츠 원본·런 변경·전투 변경 참조. 행동과 설명이 함께 사용 |

- 행동 객체는 등록 시 공유하는 무상태 규칙이다. 각 캐릭터의 스택·남은 기간을 행동 객체의 필드에 넣지 않는다.
- StatusGroup / StatusGrant는 StatusBehavior의 하위 클래스가 아니다. 데이터와 행동은 **키 조회로 연결**한다.
- 런 상태는 영구 변경을, 전투 상태는 전투 변경을 보관한다. 부여된 상태의 남은 턴과 변경의 유지 기간은 다른 데이터다.
- 원본·런 변경·전투 변경은 상위/하위 클래스가 아니다. EffectiveStatusRules가 읽는 세 입력이다. 카드도 OwnedCard가 세 입력에서 유효 CardDefinition을 제공한다.
- EffectiveStatusRules는 범용 규칙을 파티원 조회에만 합성한다. 적도 같은 행동 코드를 사용하지만 플레이어 파티의 변경은 읽지 않는다.
- 범용/개별 구분은 적용 범위다. 공통 표시 분류를 재사용하려고 모든 효과와 상태를 한 클래스 계층으로 합치지 않는다.

### 6. 값·중첩·기간의 표현

**제안 데이터 계약:** 아래 이름은 추천안을 선택하면 확정할 API의 기준이다.

- StatusGroup: `Key`, 읽기 전용 `Grants`. StackCount 합계는 현재 유효한 부여들의 합계다.
- StatusGrant: 결정론적 순번 `GrantId`, 양수 `StackCount`, 타입이 있는 `Values`, 독립된 만료·남은 횟수. 계정·시간·Guid를 ID 생성에 쓰지 않는다.
- StatusValues: 기본값 참조 또는 명시값을 구분한다. 명시값이 없는 항목만 유효 상태 규칙의 기본값을 사용한다. 기본값 변경을 이미 확정된 명시값에 중복 가산하지 않는다.
- ScalarValues: 방어·독·힘 같은 `Amount`. OrderShiftValues: 가속·둔화의 부호 있는 `Delta`. PresenceValues도 수치 Value를 가진다. 존재형의 값과 중첩 수는 저장하지만 활성 판단은 유효 부여의 존재로 한다. 값이 없다는 이유로 재부여를 버리지 않는다.
- 기간은 값 객체의 숫자 슬롯이 아니라 공통 만료 데이터로 보관한다. ‘가속 정도’와 ‘남은 턴’은 동시에 입력·저장·표시 가능하다.
- ApplyStatusPayload는 상태 키, 값 입력, 중첩 증가량, 기간 입력을 각각 표현한다. 한 번의 부여가 중첩 N을 담으면 1회 값은 모든 단위에 같으며, 서로 다른 값은 별도 부여로 저장한다. 기존 단일 EffectValue 콘텐츠는 상태별 저작 변환 경로에서 명시적 구조로 변환하고 동등성 테스트를 둔다.
- 반복형의 1회 효과량은 Values에서 읽는다. 반복 횟수는 행동이 StackCount에서 결정한다. 방어 수치를 반복 횟수로 사용하지 않는다.
- 같은 값·기간인 부여를 저장 최적화로 합칠지는 초기 구현에 포함하지 않는다. 부여 기록별 만료·제거가 먼저 정확해야 한다.

| 상태 예시 | 저장 | 코드가 정하는 중첩 의미 | 설명 |
|---|---|---|---|
| 방어 | 각 부여의 방어량과 만료 | 유효 방어량 합산, 피해 흡수 시 실제 잔량 차감 | 현재 방어량과 유지 조건 |
| 가속·둔화 | 각 부여의 정도와 남은 턴 | 제안: 유효한 정도를 합산. 각 부여는 자기 기간에 만료 | 정도와 기간이 다르면 줄을 나누어 표시 |
| 요새화 | 획득마다 부여 기록·중첩 보관 | 하나 이상 존재하면 방어 만료 억제 한 번 유효 | 범용 / 중첩 N / 추가 중첩으로 기능 강화 없음 |
| 분노 | 1회 힘 증가량과 중첩 수 | 실제 HP 피해 사건마다 힘 증가 효과를 중첩 수만큼 개별 실행 | 개별 / 피해를 받을 때 힘 증가를 N회 수행 |
| 독의 대가 | 1회 독 부여량과 중첩 수 | 실제 HP 피해를 준 사건마다 독 부여를 N회 개별 실행 | 개별 / 피해를 입힐 때 독 부여를 N회 수행 |

가속·둔화의 합산, 기존 기간 유지, 요새화가 해제된 다음 준비 시점의 방어 만료는 **검토할 제안**이다. 요새화·분노·독의 대가는 사용자 예시를 검증용으로 사용하며, 이번 문서 작성만으로 실제 콘텐츠에 등록하지 않는다.

### 7. 범용·개별 효과의 저장 후보와 표시

| 추천 순위 | 파티 범용 상태의 보관 | 장점 | 단점 |
|---|---|---|---|
| 1 | CombatState의 파티 공용 StatusBag에 한 번 보관하고 파티원 조회에 합성 | 중첩·기간을 한 번 관리, 중도 합류 파티원도 같은 범용 규칙, 적 배제 명확 | 개별 가방만 읽던 행동·설명을 파티 상태를 포함하는 조회로 이행해야 함 |
| 2 | 사용 시 모든 파티원의 StatusBag에 부여 기록 복사 | 기존 개별 조회를 활용하기 쉬움 | 제거·기간·런 변경 동기화 필요, 중도 합류와 개체 사망에서 범용 효과의 대표 상태가 모호해짐 |

1. 범용 카드 효과는 적용 범위 PartyWide, 개별 효과는 Individual을 구조화 데이터로 제공한다. 이는 대상 데이터이며 중첩 실행 규칙을 JSON으로 넘기는 것이 아니다.
2. PartyWide 규칙형 상태는 파티 공용 저장소에 기록한다. 범용 상태의 만료 시계는 전투 시점마다 한 번만 방문하고, 파티원 수만큼 기간을 줄이지 않는다.
3. 각 파티원의 유효 상태 조회는 파티 공용 상태와 자신의 개별 상태를 함께 읽는다. 적 조회에는 플레이어 파티 공용 상태를 포함하지 않는다.
4. 파티에 방어량을 직접 지급하는 효과는 파티원 각각에게 독립 방어량을 만든다. 공용 저장소를 공유 방어 잔량으로 사용하지 않는다.
5. 파티 범용 효과와 개인 효과가 같은 수치를 바꾸면 원본 → 런 범용 → 런 개인 → 전투 범용 → 전투 개인 순서를 추천한다. 이 순서는 구조 선택 시 승인하며, 명시적 치환과 가산을 구별한다.
6. 표시 조각은 범용/개별, 파티/대상, 수치·기간·중첩 의미를 갖는다. UI는 같은 상태 영역 또는 별도 범용 영역 어느 쪽에도 배치할 수 있다. 색상만으로 구분하지 않는다.
7. 상태가 하나의 그룹으로 보이더라도 파티 기여와 개인 기여를 표시 데이터에서 보존한다. 파티 효과가 해제되면 개인 기여는 유지한다.
8. 대상이 없는 원본 카드 미리보기는 확정된 실제 적용 결과처럼 표시하지 않는다. 실행 중에는 준비된 유효 데이터를 사용한다.
9. EffectDescriptionFragment / CardDescriptionLayout을 확장하고 상태 설명 생성 경로를 추가한다. StatusDescriptionRegistry 삭제는 이름 중복 정리이며 상태 설명 생성기의 삭제가 아니다.
10. 상태 행동 코드는 파티와 적에게 동일하다. 범용 효과의 적용 대상에서 적을 제외하는 것은 규칙 차별이 아니라 명시적인 대상 선택이다.

### 8. 부여에서 설명까지 실행 과정

1. CardExecutor가 OwnedCard의 유효 CardDefinition을 받아 효과를 실행한다.
2. EffectExecutor가 대상 목록을 확정하고 ApplyStatusHandler를 호출한다.
3. ApplyStatusHandler가 EffectiveStatusRules의 기본값과 구조화된 부여 입력을 사용해 한 StatusGrant를 만든다. 파티 범용 규칙 상태는 공용 저장소에 한 번 기록하고, 파티원에게 수치를 직접 지급하는 효과는 개별 부여를 생성한다. 적용 범위에 따라 파티 공용 또는 개인 StatusBag의 같은 키 StatusGroup에 추가한다.
4. 값 집계가 필요한 시점에 StatusRegistry가 해당 행동을 찾아 그룹을 해석한다. 데이터 보관자가 중앙 키 switch로 상태별 동작을 결정하지 않는다.
5. StatusApplied 등 표시 이벤트에 부여 ID·중첩 변화·기간·값을 담는다. 현재 단일 Count/Magnitude 이벤트 필드는 이행 단계에서 교체한다.
6. Presenter가 이벤트 또는 준비된 표시 스냅샷을 받아 설명 조각을 갱신한다. 설명 코드는 변경 목록을 다시 합성하거나 상태를 재실행하지 않는다.

### 9. 피해 사건에서 N회 반응까지 실행 과정

1. DamageService가 실제 HP 감소를 기록해 HpDamaged 사건을 만든다. 방어로 전부 막으면 이 사건은 없으므로 ‘피해를 받을 때’ 반응도 없다.
2. ReactionRegistry의 코드 등록은 각 반응의 관찰 역할을 정의한다. 파티원의 반응 조회에는 유효한 파티 공용 부여도 포함하며, 적은 제외한다. 분노는 SignalTarget, 독의 대가는 SignalSource에서 보유자를 찾는다. 한 사건에서 같은 후보를 두 번 수집하지 않는다.
3. ReactionDispatcher는 사건 순서 → 관찰 역할의 명시적 순서(Target 다음 Source 제안) → 상태 그룹의 최초 부여 순서 → 부여 순서로 후보를 확보한다. GrantId·중첩 수·1회 효과값을 후보 스냅샷에 포함한다.
4. 해당 반응 행동이 반복 계획을 만든다. 분노 2라면 ‘힘 1 부여’와 ‘힘 1 부여’ 두 실행을 돌려준다.
5. Dispatcher는 각 실행 전에 부여가 남아 있는지와 행동의 생존·대상 조건을 다시 확인한다. 첫 실행으로 상태가 사라지거나 대상이 죽으면 행동 조건에 따라 다음 실행을 건너뛴다.
6. 매 실행은 EffectExecutor.ApplyReaction을 각각 통과한다. 첫 실행의 상태 부여·직접 반응·사망 정리를 마친 뒤 두 번째 실행을 시작한다. 두 실행의 표시 이벤트와 규칙 사건은 별도로 남는다. ApplyReaction의 actorId에는 사건 TargetId가 아니라 이번 후보의 보유자 ID를 전달한다. 독의 대가의 보유자는 SourceId, 독을 받는 대상은 TargetId다.
7. 반복 도중 새로 얻은 중첩은 현재 사건의 후보 수를 늘리지 않는다. 다음 사건에서 반영한다.
8. Reaction 기원의 사건을 일괄 차단하지 않는다. 반응 대상 사건·재진입 조건은 해당 행동이 정한다. 자기 사건을 무한히 생성하는 능력은 승인된 조건으로 차단하고 회귀 테스트한다.

근거: DamageService는 실제 HP 감소일 때 사건을 만든다(`Assets/Core/Effects/DamageService.cs:115`). 기존 EffectExecutor는 각 반응 효과에 별도 실행 경계를 제공한다(`Assets/Core/Effects/EffectExecutor.cs:112`). 현재 전투 실행 계약 §7의 경계는 유지하되 관찰 역할과 중첩 반복을 확장한다.

### 10. 대표 실행 예시

**카드 변경 — 기존 예시 유지**

- 원본 피해 3. 소유 카드 A에 런 변경 +2, 전투 변경 +4를 등록한다.
- A의 실행과 설명은 피해 9, 같은 원본을 가진 B는 피해 3이다.
- 전투 종료 후 A는 피해 5, 새 런은 원본 피해 3으로 시작한다.

**가속 — 수치 두 종류와 독립 만료 (제안)**

- A에게 가속 ‘정도 2, 남은 턴 3’을 부여한 뒤 ‘정도 4, 남은 턴 1’을 부여한다.
- StatusBag의 가속 그룹은 두 부여 기록을 보관한다. 행동은 Delta -2와 -4를 합쳐 실행 순서를 6 앞당긴다.
- 설명은 ‘가속 2 / 3턴’, ‘가속 4 / 1턴’을 분리해서 보여준다.
- 지정 만료 시점 한 번 후 두 번째 부여만 제거한다. 첫 번째는 정도 2 / 남은 턴 2로 유지한다.

**분노 — 합산하지 않는 두 실행**

- A가 분노를 두 번 얻는다. 각 부여의 1회 값은 힘 1이다.
- A가 HP 피해 3을 받으면 DamageService가 HpDamaged(Source=적, Target=A, Amount=3)을 만든다.
- RageReaction은 A의 유효 부여 두 개에서 각각 힘 1 실행을 계획한다.
- EffectExecutor가 첫 힘 1 부여 → StatusGained 사건과 직접 반응 → 두 번째 힘 1 부여 → 별도 사건과 반응 순서로 수행한다.
- 힘의 최종량은 2 증가해도, 힘 +2 한 번과 달리 힘 획득 반응은 두 번의 사건을 관찰한다.

**독의 대가 — 공격한 쪽의 반응**

- A가 독의 대가 2를 보유한 채 적 B에게 실제 HP 피해를 준다.
- SignalSource 역할로 A의 상태를 찾고, 대상 B에게 독 1을 두 번 별도 부여한다.
- 두 부여 모두 정상 적용됐다면 독의 최종량은 2 증가한다. 각 부여는 독 획득 보정과 사건 처리를 각각 거친다.

**요새화 — 저장 중첩과 실행 중첩의 구분**

- 요새화를 두 번 얻으면 중첩 2를 보관한다. 만료 억제 규칙은 두 배가 아니라 활성 상태 하나로 해석한다.
- 한 부여를 제거해도 다른 부여가 남으면 억제는 유지된다. 마지막 부여를 제거한 뒤 억제가 해제된다.
- 범용 요새화는 파티 전원의 방어 만료에 적용되고 적의 방어 만료에는 적용되지 않는다. 한 파티원에게 개별 상태가 함께 있어도 마지막 범용 부여 제거가 개별 부여를 제거하지 않는다.

### 13. 구현 범위와 검증 규칙

- 제품 코드는 전용 워크트리에서 작성한다. 메인 체크아웃의 Assets·Packages·ProjectSettings를 수정하거나 브랜치를 전환하지 않는다.
- 각 단계는 실패 테스트 → 최소 구현 → 관련 헤드리스 검증 → Tools/verify.sh 전체 → 한국어 커밋으로 진행한다.
- 전체 세이브 UI·다국어·범용 스크립트 엔진·강화 콘텐츠 카탈로그·무관한 인터페이스 정리는 제외한다. 영구 변경 데이터의 직렬화 왕복은 포함한다.
- 구조 검토와 실행 예시의 승인이 먼저다. master 머지는 별도 사용자 승인 후 수행한다.
- 문서 형식은 이번 사용자 피드백을 우선 적용한다. 색인과 진행 상태를 같은 커밋에서 갱신한다.
