# 카드·상태 변경과 Stacks 합산 구조 — 설계 후보와 작업 계획

사람 검토용: [HTML 설계도](2026-10-07-card-status-mutation-roadmap.html)

## 상세

### 1. 이번 수정에서 확정한 요구

- 개정일: 2026-10-08. 제품 코드가 아니라 수정된 설계 후보·작업 계획이다.
- 한 보유자의 상태는 키당 인스턴스 하나, UI 심볼 하나와 숫자 하나로 표시한다. 같은 상태를 다시 받으면 별도 부여를 만들지 않고 Stacks를 합산한다.
- ‘재부여 제거’는 효과의 다시 적용을 막는 뜻이 아니다. 별도 부여 기록과 갱신/교체 분기를 없애고 기존 인스턴스에 수치를 더한다는 뜻이다.
- 부여자·출처별 상태 기록을 저장하지 않는다. StatusGroup/StatusGrant, 부여별 값·기간·ID, 부여별 만료 제안은 철회한다.
- N회 실행 제안도 철회한다. 합산된 Stacks를 상태 행동이 해석하고 필요하면 한 번의 효과 수치로 계산한다. Stacks만큼 반복 실행하지 않는다.
- 필드명은 `Stacks`로 확정한다. 인스턴스의 게임 수치는 Stacks 하나이며 기존 Count·Magnitude·VisitsLeft를 제거한다. 키와 처리 시점·처리 방식의 메타데이터는 유지하되 별도 남은 기간 카운터는 두지 않는다.
- 방어량과 독립된 N턴 만료는 지원하지 않는다. 기간을 가진 상태는 Stacks 자체가 남은 기간이다. 특정 시점에 무조건 제거하는 상태는 별도 감소 카운터 없이 제거한다.
- 상태의 기본 정도·성장량·배율 등은 중앙 규칙 데이터, 현재 Stacks는 개별 인스턴스가 가진다. Stacks의 의미는 상태 행동이 결정한다.
- 파티 범용 효과는 플레이어 파티 전체에 적용하고 적은 제외한다. UI를 기존 상태 영역에 합칠지 별도 영역으로 만들지는 미결정이다.
- 상태 호버 설명은 현재 Stacks를 삽입하지 않는 규칙 설명이다. 중앙 규칙이 전투 중 바뀌면 그 규칙 수치는 새 설명에 반영한다. ‘Stacks와 무관하게 고정’은 ‘영원히 원본 문구로 고정’이라는 뜻이 아니다.
- 카드 설명의 상태 부여량/기간(예: 둔화 2 부여)과 상태 심볼의 호버 설명은 별도다. 전자의 부여량은 유지하고 후자에 현재 인스턴스 Stacks를 다시 풀어 쓰지 않는다.
- 한 카드가 중앙 정도와 대상 Stacks를 모두 바꿀 수 있다. 두 값을 서로 다른 저장 위치에 변경한다. 모든 부여가 두 값을 저장하도록 바꾸지 않는다.
- 이번 사용자 요구가 이전 개정의 부여별 보관·N회 실행 요구를 대체한다. 카드 원본/런 변경/전투 변경, 코드 규칙·JSON 수치, 상속·참조 설계도, 구조 후보 비교는 유지한다.

### 3. Stacks 합산과 만료 처리

- **추천한다.** 하나의 UI 수치와 하나의 저장 값이 대응하고, 여러 번 받았을 때 별도 기록·기간·출처 규칙을 만들 필요가 없다.
- 방어와 독의 기존 수치 합산은 Stacks 합산으로 옮긴다. 둔화는 Stacks를 기간으로 해석하므로 다시 받으면 남은 기간이 늘고 실행 순서 변화량은 중앙 값 그대로다.
- ‘중첩 수’는 모든 상태에서 ‘발동 횟수’라는 뜻이 아니다. 방어에서는 흡수 잔량, 독에서는 피해량, 둔화에서는 남은 턴으로 해석한다.
- 요새화는 Stacks를 합산해도 Stacks>0의 활성 여부로 해석한다. 같은 상태를 여러 번 얻었다고 만료 억제가 배수로 강해지지 않는다.
- 분노 같은 합산형 반응이 필요하다면 Stacks 2를 읽어 힘 증가량 2 한 번으로 계산한다. 기존 제안의 힘 1 두 번과 다른 규칙이며, 후자를 위한 반복 실행 테스트는 삭제한다. 예시 능력의 실제 콘텐츠 추가는 별도 구현 범위에서 결정한다.
- 기존 코드의 Add는 기간도 갱신하므로, 이 분기를 없앨 때 Stacks뿐 아니라 만료 정책의 처리도 명시한다. 제안: 기존 인스턴스의 정책은 유지하고 Stacks만 더한다. 방어의 ‘다음 준비에 사라짐’은 정책으로 처리한다.
- 정책 자체 변경이 필요한 카드는 명시적인 정책 변경 효과를 사용한다. 상태를 다시 받는다는 이유로 모든 정책을 다시 만들지 않는다.

**감소와 제거의 계약 — 별도 VisitsLeft 없음**

| 상태 | Stacks 의미 | 처리 시점 | 처리 |
|---|---|---|---|
| 둔화·가속 | 남은 기간 | 기존 턴 정리 시점 | Stacks 1 감소, 0 이하면 제거 |
| 방어 | 남은 방어량 | 피해 흡수 / 다음 턴 준비 | 흡수량만큼 차감 / 남은 Stacks와 무관하게 제거 |
| 독 | 현재 독 수치 | 턴 종료 행동 | Stacks만큼 피해 후 중앙 성장량만큼 증가; 기간 카운터 없음 |
| 소모형 상태 | 남은 사용 횟수 | 기존 발동 성공 경계 | Stacks 1 소모, 0 이하면 제거 |
| 존재형 상태 | 누적 수치 | 해당 상태의 제거 정책 | Stacks>0이면 활성; Stacks만큼 반복하지 않음 |

- 반복 적용은 같은 인스턴스의 Stacks만 합산한다. 둔화 3+3은 6이 되고 다음 감소 시점에는 5가 된다.
- 만료 처리는 ‘시점이 오면 Stacks 감소’와 ‘시점이 오면 즉시 제거’를 구분한다. 기간 상태의 0 판정과 사용 횟수의 0 판정은 같은 수치 원본을 사용한다.
- 중앙 규칙/행동은 처리 방식과 시점을 결정한다. StatusLifetimePolicy는 해당 정책을 공통 시점에서 처리하며 상태 키 switch를 추가하지 않는다.
- 기존 Kind·Expiry·Lifetime 변환에서 동일한 기간을 중복 보관하는 표현을 정리한다. 새 남은 턴 필드나 종료 턴 필드로 VisitsLeft를 우회 대체하지 않는다.
- 시점 진입 시 존재하던 상태를 처리하는 현재 스냅샷 규칙은 유지한다. 처리 도중 새로 받은 상태를 같은 시점에 즉시 제거하지 않는다. 근거: Assets/Core/Status/StatusLifetimePolicy.cs:25.


### 4. 상태 저장 구조 후보 — 추천 순서

| 순위 | 후보 | 장점 | 단점 | 판단 |
|---|---|---|---|---|
| 1 | 기존 StatusInstance 유지 + Stacks 단일 게임 수치 + 등록형 행동 | 사용자 요구와 직접 일치, 키별 조회·UI 유지, 불필요한 부여 기록 없음 | Magnitude를 읽는 행동·이벤트·테스트를 함께 이행해야 함 | 추천 |
| 2 | Stacks 인스턴스와 별도 상태별 처리 정책 객체 조합 | 시점 처리를 재사용하기 쉬움 | 정책 객체 수와 연결이 늘어남 | 동일한 정책이 반복될 때만 추출 |
| 3 | 상태별 인스턴스 하위 클래스마다 Stacks 해석 구현 | 데이터 타입별 동작이 명시적 | 상태 데이터와 행동 계층이 겹치고 등록·직렬화가 복잡해짐 | 현재 요구에는 과함 |

단일 Stacks와 VisitsLeft 제거는 확정이다. 후보는 이를 구현하는 코드 책임 분배만 비교한다. StatusGroup/StatusGrant, N회 발동 계획 객체를 만들지 않는다. JSON의 기존 만료 데이터는 감소/제거 시점을 표현하는 데이터로 이행하고 독립 남은 기간은 두지 않는다. Stacks 해석과 중첩 동작은 상태별 C# 행동이 맡는다.

### 5. 추천안의 객체와 참조 관계

| 객체 | 역할 | 소유·참조·상속 |
|---|---|---|
| StatusContentCatalog | 저작된 상태 이름·기본 규칙 보관 | 상태 스펙을 키로 보관. 원본 조회 전용으로 사용 |
| RunState / CombatState | 기간별 변경 데이터 보관 | 런 변경 / 전투 변경과 파티 범용 데이터 보관 |
| StatusRuleResolver (제안) | 적용 대상의 유효 중앙 규칙 조회 | 원본과 런·전투 변경을 읽음. Stacks는 저장하지 않음 |
| StatusBag | 한 대상의 상태 인스턴스 보관 | 키당 StatusInstance 하나. 같은 키의 Stacks만 합산 |
| StatusInstance | 부착된 상태의 현재 수치 보관 | Key·Stacks·처리 시점/방식. Count·Magnitude·VisitsLeft·출처·별도 기간 없음 |
| StatusLifetimePolicy | 공통 시점의 감소·제거 처리 | 기간형은 Stacks 차감, 고정 시점형은 즉시 제거. 별도 카운터 없음 |
| StatusBehavior | Stacks 해석과 해당 상태의 규칙 계산 | IStatusBehavior 구현 기반 클래스. Poison/Block/Slow 등이 상속 |
| StatusRegistry | 상태 행동 조회 | 키로 공유 행동 객체 참조. 캐릭터 Stacks를 보관하지 않음 |
| EffectExecutor / ReactionDispatcher | 효과와 사건 처리의 호출 순서 조정 | 기존 실행 경계 사용. Stacks만큼 반복하는 규칙 추가 없음 |
| StatusDescriptionComposer (제안) | 유효 중앙 규칙의 호버 설명 생성 | 규칙과 이름을 읽음. 현재 Stacks를 문장에 넣지 않음 |

중앙 관리의 의미는 위 데이터 조회와 등록형 행동의 협업이다. 하나의 StatusManager에 데이터 보관·모든 상태 계산·문장 생성을 넣지 않는다. UI 컨트롤러에 규칙 판단을 추가하지 않는다.

### 6. 중앙 정도와 개별 기간이 함께 바뀌는 카드

**현재 가능한 것**

- 둔화 인스턴스에 기간 Count를 주는 경로는 존재한다. 실행 순서 정도는 별도로 중앙 스펙에서 읽는다.
- 그러나 ApplyStatusPayload는 상태 키만 받고 EffectValue는 하나다. 이 효과 하나에서 중앙 정도까지 동시에 변경하는 입력은 현재 없다.
- 중앙 Rules.Set은 배율 규칙을 바꿀 수 있지만, 둔화 정도·독 성장량은 카탈로그의 읽기 메서드만 제공된다. ‘정도와 기간을 모두 바꾸는 일반 카드 효과 경로가 이미 완성됐다’고 말할 수는 없다.

근거: Assets/Core/Effects/ApplyStatusPayload.cs:10, Assets/Core/Authoring/Statuses/StatusContentCatalog.cs:43, :62, :65. 배율 저장 구조: Assets/Core/Status/StatusRuleSet.cs:25.

**추천 경로 — 한 카드의 효과 두 개**

1. ModifyStatusRule 효과가 플레이어 파티의 둔화 정도를 전투 동안 변경한다. 변경 데이터는 CombatState 쪽에 보관한다.
2. ApplyStatus 효과가 지정한 파티원의 둔화 Stacks를 증가시킨다. 기간은 해당 인스턴스에 보관한다.
3. 해결은 기존 효과 목록 순서로 수행한다. 두 효과는 별개 경계이며, 카드 설명은 ‘파티 규칙 변경’과 ‘대상 상태 부여’를 구분한다.
4. 정도의 변경이 파티 전체인지 개인에게만 적용되는지는 효과의 명시적 적용 범위를 따른다. 이 예시는 범용 규칙 변경이다.
5. 중앙 정도가 바뀌면 해당 범위에서 이미 활성화된 둔화도 다음 계산부터 새 정도를 사용한다. 기간 Stacks는 자동 갱신하지 않는다.

대안: 두 명령을 하나의 복합 효과로 만들면 단일 적용을 표현할 수 있으나 별도 복합 핸들러·실패 규칙이 필요하다. 현재는 기존 효과 목록을 활용하는 두 효과 방식을 추천한다. 한 카드라는 이유만으로 원자적 동시 변경을 새로 보장하지 않는다.

### 7. ‘전투가 원본 카탈로그의 수치 표를 반환한다’의 의미

**현재 구조를 물건에 비유하면**

- StatusContentCatalog는 상태 기본 규칙을 적어 둔 공용 규칙표다.
- CombatState는 전투 진행 기록이다. 현재 StatusRules를 요청하면 자기 전용 표를 주지 않고 공용 규칙표의 Rules를 그대로 건네준다.
- 따라서 전투마다 CombatState가 새로 생겨도, 카탈로그가 같으면 Rules도 같은 객체다. 복사본이 아니다. JSON 파일을 고친다는 뜻이 아니라 메모리의 공유 객체를 고친다는 뜻이다.

직접 근거: `CombatState.StatusRules => StatusContent.Rules` (Assets/Core/Combat/CombatState.cs:63). Rules를 실제로 만드는 곳은 카탈로그 생성자(Assets/Core/Authoring/Statuses/StatusContentCatalog.cs:32)다. 전투 노드 흐름은 콘텐츠를 로드한 뒤 같은 콘텐츠로 새 런·다음 노드를 시작한다(Assets/Unity/Scripts/Battle/CombatNodeFlow.cs:51, :73, :82).

**가상 실행 예시 — 이미 발생한 게임 버그라고 주장하는 것이 아님**

1. 콘텐츠의 취약 기본 배율이 150이라고 하자.
2. 전투 A가 StatusRules.Set으로 ‘이번 전투만 200’을 쓰면, A의 전용 표가 아니라 카탈로그의 공용 표가 바뀐다.
3. 다음 전투 B가 같은 카탈로그를 받으면 200을 읽는다. A의 인스턴스 수치를 초기화해도 규칙표는 초기화되지 않는다.
4. 전투 종료 때만 지워야 할 변경과 런 동안 남아야 할 변경을 구별할 저장 위치가 현재 없다.
5. 해결책은 원본 150을 유지하고 런·전투 변경을 별도 저장한 뒤 필요한 범위의 유효 규칙을 읽는 것이다. 전투 A 종료 시 A의 전투 변경만 버린다.

프로덕션 코드에서 StatusRules.Set / 카탈로그.Rules.Set의 런타임 변경 호출은 검색 결과 없으며, 생성 시 원본 배율을 초기화하는 Rules.Set은 있다. 코드 주석과 백로그도 게임 중 변경이 아직 없음을 명시한다. 이 작업은 이미 발생한 표시 버그를 고친다는 뜻이 아니라, 변경 기능을 구현할 때 기간을 구분할 기반을 마련하는 것이다. 근거: Assets/Core/Combat/CombatState.cs:45, [백로그 §15.1](2026-07-16-architecture-refactor-backlog.md).

### 8. 파티 범용 효과와 개별 효과

| 추천 순위 | 저장 후보 | 장점 | 단점 |
|---|---|---|---|
| 1 | 파티 공용 상태·규칙을 한 번 보관하고 파티원 계산에 참조 | 기간·합산을 한 번 관리, 적 제외 명확 | 개별 상태만 읽던 조회 접점 수정 필요 |
| 2 | 파티원 각각의 상태/규칙에 같은 변경 복사 | 기존 조회 활용 | 해제·기간·멤버 변경의 동기화 필요 |

- 범용 요새화·독 성장량 변경은 플레이어 파티에만 적용한다. 적도 같은 상태 행동을 사용할 수 있지만 플레이어 파티 변경은 읽지 않는다.
- 개별 방어량 증가 등은 지정한 대상에 적용한다. 파티에 방어를 지급하더라도 방어 잔량을 여러 캐릭터가 공유하지 않는다.
- 파티 공용 상태도 같은 키 하나, Stacks 합산이다. 감소/제거 시점은 파티원 수만큼 반복 처리하지 않는다.
- 효과 표시 데이터에 범용/개별·대상·변경 기간을 보관한다. 별도 UI 신설 여부는 이번 계획에서 확정하지 않는다.
- 상태 숫자는 심볼 옆에 표시한다. 호버는 Stacks와 무관한 규칙 설명을 제공한다. 파티·개인 기여가 겹칠 때도 별도 심볼을 무조건 추가하지 않고 표시 결합 정책을 검토한다.

### 9. 호버 설명 후보 — 추천 순서

| 순위 | 둔화 호버 문구 | 장점 | 고려할 점 |
|---|---|---|---|
| 1 | 이 대상의 실행 카드 순서가 +2 됩니다. 둔화 수치는 매 턴 1 감소합니다. | 대상·효과·숫자의 감소가 명확함 | 두 문장이라 조금 길다 |
| 2 | 실행 순서 +2. 매 턴 둔화 1 감소. | 짧고 툴팁에 적합함 | 순서와 대상의 의미는 UI 맥락에 의존 |
| 3 | 실행 카드의 순서가 +2 됩니다. 표시된 수치는 남은 턴 수입니다. | 심볼 숫자가 기간임을 직접 설명 | 턴마다 감소한다는 표현이 간접적 |

- 위 +2는 중앙 규칙의 값이지 인스턴스 Stacks가 아니다. 둔화 Stacks가 2여도 5여도 설명은 같다.
- 중앙 정도가 +3으로 변경되면 해당 범위의 호버는 +3으로 바뀐다. Stacks 감소 때문에 매 턴 문구가 달라지지는 않는다.
- ‘매 턴 1 감소’와 실제 감소 시점은 현재 공통 만료 시점을 따른다. 내부 시점 용어를 사용자 문장에 노출하지 않는다.
- 카드의 ‘둔화 2 부여’ 문장은 부여량 설명으로 유지한다. 상태 호버의 고정 설명과 혼동하지 않는다.

### 10. 실행 과정과 구체 예시

**상태 부여와 계산**

1. 카드의 ApplyStatusHandler가 상태 키와 증가량을 받는다.
2. StatusBag이 같은 키를 찾고 있으면 Stacks를 더한다. 없으면 하나의 인스턴스를 만든다.
3. 계산 시 StatusRegistry가 해당 행동을 찾는다. 행동은 인스턴스 Stacks와 StatusRuleResolver의 유효 중앙 규칙을 읽는다.
4. 행동은 한 번 계산해 결과를 낸다. 등록된 만료 정책과 행동에 따라 Stacks가 감소·증가·소모된다.
5. 이벤트/표시 데이터로 심볼 숫자를 갱신한다. 호버 설명은 유효 규칙에서 생성한다.

**둔화**

- 중앙 정도는 +2, A의 둔화 Stacks는 2다. 다시 둔화 3을 부여하면 같은 인스턴스의 Stacks가 5가 된다.
- 실행 순서 변화는 여전히 +2다. Stacks 5를 +10이나 5회 실행으로 해석하지 않는다.
- 턴 정리 시점에 Stacks 자체를 줄여 4가 된다. 호버 설명은 그대로다.
- 별도 효과가 중앙 정도를 파티 범위 +3으로 바꾸면 A의 설명·계산은 +3, Stacks는 4를 유지한다. 적의 기본 정도는 유지한다.

**방어와 독**

- A에게 방어 3 후 2를 부여하면 Stacks는 5다. 피해 4를 흡수하면 1, 다음 준비 시점에는 정책에 따라 사라진다.
- B에게 독 2 후 3을 부여하면 Stacks는 5다. 틱에서 피해 5를 주고 성장량이 1이면 Stacks는 6이 된다. 원인 캐릭터를 저장하지 않는다.

**카드 변경 — 기존 예시 유지**

- 원본 피해 3. 소유 카드 A에 런 변경 +2, 전투 변경 +4를 적용하면 실행과 설명은 피해 9다. 같은 원본의 B는 3이다.
- 전투 종료 후 A는 5, 새 런은 원본 3으로 시작한다.

### 13. 유지하는 경계와 제외하는 작업

- 상태 부여자 기록은 만들지 않는다. 피해 사건의 SourceId는 현재 피해 원인을 표현하며 상태 부여 이력이 아니다. 기존 사건 정보를 삭제할 필요는 없다(Assets/Core/Events/CombatSignal.cs:3).
- TargetId 기반의 현재 반응을 유지한다. 이전 계획의 Source 역할 확장·N회 실행은 제외한다. 이후 ‘피해를 입힐 때’ 능력을 추가할 경우 사건 행위자 관찰을 별도 요구로 설계하며, 부여자 추적과 혼동하지 않는다.
- 반복 부여가 한 번의 수치 합산이 되므로 부여별 기간·출처가 섞였을 때의 구별·전이 규칙은 만들지 않는다.
- 별도 수치를 유지하면서 N턴 후 만료하는 상태는 지원하지 않는다. VisitsLeft·RemainingTurns·ExpiresAtTurn 등의 독립 기간 저장을 추가하지 않는다.
- 새 능력 콘텐츠·전체 세이브 UI·다국어·범용 스크립트 엔진·무관한 리팩터링은 제외한다.
- 제품 코드는 전용 워크트리에서 구현한다. 메인 Assets를 수정하거나 브랜치를 전환하지 않는다.
- 각 구현 단계는 실패 테스트 → 최소 구현 → 관련 헤드리스 검증 → Tools/verify.sh 전체 → 한국어 커밋으로 진행한다.
- master 머지는 별도 사용자 승인 후 수행한다. 현재는 수정된 후보 문서의 검토 단계다.
