# 카드·상태 변경과 설명 일치 작업 계획

## 상세

### 1. 목적과 문서의 범위

- 작성일: 2026-10-07
- 이 문서는 작업 순서·설계 결정·검증 기준을 정하는 로드맵이다. 카드와 상태 각각의 구현 계획은 아래 단계 A에서 확정한 설계를 근거로 별도 작성한다.
- 목표: 전투 중 카드·상태 변경을 실행과 설명에 함께 반영하고, 런 변경과 전투 변경의 유지 기간을 구분한다.
- 사용자 요구: 수치·지속 기간·적용 및 소모 방식의 변경, 카드의 대상 변경과 추가 상태 부여를 지원한다. 다국어는 낮은 우선순위다.
- 카드 변형의 기본 모델은 [기존 설계 §4.3](../specs/2026-07-30-card-mutation-and-runtime-content-design.md#43-카드의-세-형태와-두-수명)을 따른다. 기존 JSON 로딩을 다시 구현하지 않는다.
- 상태 적용 범위와 부여된 상태를 바꾸는 규칙은 아직 확정하지 않았다. 사용자는 2026-10-07 이 범위를 추가 논의하기로 했다. 이 문서의 제안은 승인된 게임 규칙을 뜻하지 않는다.
- 이 로드맵은 기존 설계를 대체하지 않는다. 충돌하는 결정은 단계 A에서 해당 기준 문서와 함께 수정한다.

### 3. 공통 원칙

1. **변경 기간과 상태 지속 기간을 구분한다.** `Permanent` 변경은 이 런에만 유지되는 변경이다. `StatusLifetimeKind.Permanent` 상태와 같은 뜻이 아니며, 계정 영구 성장도 아니다.
2. 카드의 유효 데이터는 원본 → 런 변경 → 전투 변경 순서로 만든다. 같은 목록 안의 변경은 등록 순서로 적용한다. 원본을 수정하지 않는다.
3. 런 변경은 전투 중 추가해도 즉시 적용되고 다음 전투에 남는다. 전투 변경은 정상 종료에 제거하고 다음 전투 진입에서도 방어적으로 제거한다.
4. 카드 변경과 상태 변경은 별도 데이터 타입으로 만든다. 기간 구분 원칙을 공유한다는 이유만으로 범용 변경 엔진·제네릭 저장소·새 서비스 인터페이스를 만들지 않는다.
5. 설명은 변경 목록을 합성하지 않는다. 코어가 만든 유효 카드·상태 규칙과 현재 상태의 표시 데이터를 받아 설명한다.
6. 기존 효과 핸들러·상태 행동·설명 컴포저를 유지한다. 새 효과와 행동의 확장은 등록 패턴을 따른다.
7. UI 컨트롤러는 호출 순서와 연결을 담당한다. 규칙 계산이나 문장 생성을 추가하지 않는다. 실행 중 변경의 표시에는 이벤트와 준비된 표시 데이터를 사용한다.
8. 원본 콘텐츠 이름은 기존 콘텐츠에서 조회한다. 이름 변경 기능은 이번 상태 변경 요구에 포함하지 않는다.
9. 전체 세이브 시스템·강화 보상 화면·강화 콘텐츠 카탈로그·덱과 캐릭터의 범용 변경 구조·다국어·무관한 인터페이스 정리는 제외한다. 영구 변경 데이터의 직렬화 왕복은 포함한다.

### 4. 단계 A — 설계 결정 (P0)

**산출물:** 카드 구현에 필요한 추가 결정, 상태 변경 설계 HTML/Markdown, 요구사항별 테스트 표. 이 단계는 제품 코드를 수정하지 않는다.

- [ ] 실제 강화 효과 예시 2~3개를 정하고 상태 변경의 범위를 사용자와 확정한다: 공통 규칙 / 부여자별 / 보유자별. 부여자의 강화가 부여된 상태에 남는지, 전이될 때도 유지되는지 명시한다. 특정 대상에 적과 소유 카드도 포함할지 명시한다.
- [ ] 규칙 변경과 부여된 인스턴스 변경을 분리한다. 기본 지속 기간 변경을 기존 상태에도 소급할지 결정한다. **제안:** 이후 부여의 기본 정책만 바꾸고, 기존 상태의 남은 기간은 명시적인 인스턴스 변경으로 바꾼다.
- [ ] 이미 부여된 상태의 행동 수치가 언제 갱신되는지 결정한다. **제안:** 독 성장량처럼 행동이 읽는 규칙은 다음 행동부터 유효값을 읽고, 남은 횟수·세기는 자동으로 다시 부여하지 않는다.
- [ ] ‘적용·소모 방식’을 구체화한다: 재부여 시 합산/교체, 만료 정책, 능동 소비의 `ConsumptionMode`. 마지막 항목은 현재 효과 데이터에 있으므로 무조건 상태 스펙으로 옮기지 않는다.
- [ ] 특정 대상 변경을 지원한다면 공통 변경과 대상 변경의 합성 순서 및 대상 식별 방식을 설계 문서에 확정한다. 런 대상은 전투마다 재생성되는 객체 참조에 의존하지 않는다.
- [ ] 실행선에 놓인 카드를 변경하면 어느 시점의 값을 실행하는지 확정한다. **제안:** 미해결 카드는 변경을 반영하고, 해결을 시작한 카드의 해당 해결은 시작 시점 데이터로 끝낸다. 비용·실행 순서 변경에 따른 재배치와 이미 지불한 비용의 처리도 명시한다.
- [ ] 효과 변경의 선택 기준을 확정한다. 기존 설계의 `EffectKey` 선택을 유지하되 같은 키 여러 개의 첫 번째/전체를 명시하고, 결과 참조용 효과 ID를 보존한다. 참조된 효과 제거·치환을 어떻게 거부할지 정한다.
- [ ] 카드 대상 변경은 기존 진영·위치 모델을 사용하고, 추가 효과는 기존 효과 저작 스펙을 사용하도록 확정한다.
- [ ] 수정할 기준 문서를 갱신하고 HTML 개요와 Markdown 상세의 일치를 검토한다. 카드·상태의 단계별 구현 계획을 작성한다.

**완료 조건:** 위 결정이 승인된 문서에 있으며, 구현자가 게임 규칙을 임의로 정하지 않고 다음 단계를 수행할 수 있다.

### 5. 단계 B — 카드 변경 구현 (P1)

**변경 영역:** `OwnedCard`, `RunMember`, `PartyMemberLoadout`, `CombatNode`, `DeckCombatSession`, `ExecutionCardInstance`, 카드 저작 스펙·검증, 카드 표시 변환.

**새 파일 후보와 책임:** `Assets/Core/Cards/CardMutation.cs`는 변경 데이터, `CardMutation`의 구체 연산 파일은 해당 카드 변환만 담당한다. 구체 타입·메서드 서명은 단계 A의 카드 구현 계획에서 확정한다.

- [ ] `CardMutationTests`에 원본 피해 3, 런 변경 +2, 전투 변경 +4 → 유효 피해 9 테스트를 먼저 작성한다. 같은 원본을 가진 다른 소유 카드는 피해 3을 유지해야 한다.
- [ ] 실패를 확인한 뒤 원본·두 변경 목록·유효 카드 값을 구현한다. 변경 목록은 외부에서 직접 수정하지 못하게 한다.
- [ ] 효과 수치, 카드 대상, 효과 추가, 적용·소모 페이로드 변경을 검증한다. 카드 설명을 유효 카드로 생성해 효과 추가와 수치 변화가 설명에 나타나는지 함께 검증한다.
- [ ] 런에서 소유 카드 객체를 유지하도록 저장 구조와 덱 구성 경로를 바꾼다. 새 보상 카드는 새로운 소유 카드 객체로 추가한다.
- [ ] `CardMutationLifecycleTests`에 전투 중 영구 변경의 즉시 반영·다음 전투 유지, 승리/패배 종료 시 전투 변경 제거, 종료를 건너뛴 다음 진입 시 제거, 새 런 격리를 작성한다.
- [ ] 단계 A에서 확정한 실행선 변경 규칙을 배치·해결·설명에 연결한다. 1회 해결용 보정과 소유 카드 변경을 혼합하지 않는다.
- [ ] 영구 변경만 직렬화한 뒤 역직렬화하여 유효 카드·설명·실행 결과가 같은지 검증한다.
- [ ] `Tools/verify.sh` 전체 통과 후 카드 단계 커밋을 만든다.

**완료 조건:** 카드의 기간별 변경을 실제 전투 경로에서 수행할 수 있고, 설명과 실행이 일치한다. 테스트만 사용하는 변경 저장 구조로 끝내지 않는다.

### 6. 단계 C — 상태 변경 구현 (P1)

**선행 조건:** 단계 A의 상태 설계 승인. 카드와 공통 저장소를 만들 필요는 없지만, 카드 단계에서 기간별 검증 패턴을 먼저 확보한다.

**변경 영역:** `RunState`, `CombatState`, `StatusContentCatalog`, 상태 훅 컨텍스트, 배율·독·실행 순서 행동, `ApplyStatusHandler`, `ConsumeStatusHandler`, 설명 컨텍스트.

- [ ] `StatusRuleMutationTests`에 원본·런·전투 변경의 합성과 원본 불변 테스트를 작성한다. 합산/교체/기간 변경 등 승인된 지원 항목마다 실행 결과를 단언한다.
- [ ] 실패를 확인한 뒤 상태 전용 변경 데이터를 구현한다. 원본 카탈로그를 변경하지 않고 유효 상태 규칙을 얻는다.
- [ ] 배율·독 성장량·실행 순서·상태 부여가 동일한 유효 규칙 조회 경로를 사용하게 한다. 상태별 데이터 해석은 해당 행동에 둔다.
- [ ] 지원하기로 한 적용·소모 방식 변경을 실제 부여·소모에 연결한다. 기존 효과의 정책과 상태 기본 정책을 혼동하지 않는다.
- [ ] 특정 대상 변경을 지원한다면 대상 A의 변경이 B에 섞이지 않는 테스트, 공통 변경과 대상 변경이 함께 있는 테스트를 작성한다.
- [ ] `StatusInstanceMutationTests`에 승인된 기존 상태 변경 정책을 검증한다. 기본 지속 기간 변경과 남은 기간 직접 변경의 결과가 구분되어야 한다.
- [ ] 전투 종료·다음 전투 진입·런 재시작의 격리와 영구 변경 데이터의 직렬화 왕복을 검증한다.
- [ ] 상태 변경 직후 설명과 실제 적용·행동 결과가 일치하는 테스트를 포함한다. `Tools/verify.sh` 전체 통과 후 상태 단계 커밋을 만든다.

**완료 조건:** 지원 범위의 상태 변경이 수명에 맞게 유지·제거되고, 기존 상태 수치가 다른 전투나 런으로 새지 않는다.

### 7. 단계 D — 표시 연결과 통합 검증 (P1, B·C에 포함)

- [ ] `DescriptionComposer`는 완성된 유효 카드 정의를 입력받는다. 카드·상태의 변경 목록을 설명 레이어에 넘겨 재계산하지 않는다.
- [ ] 부여 설명의 정책 데이터와 실제 상태 적용의 정책 데이터가 같도록 설명 컨텍스트를 연결한다.
- [ ] 상태 규칙의 설명과 부여된 상태의 남은 기간·세기 표시를 구분한다. 현재 상태를 원본 스펙의 기본값으로 설명하지 않는다.
- [ ] 변경 이벤트·표시 데이터 갱신을 기존 Presenter/재생 흐름에 연결한다. `BattleScreenController`에는 규칙 계산을 추가하지 않는다.
- [ ] `MutationDescriptionIntegrationTests`로 수치·대상·추가 상태·지속·소모 방식 변경을 검증한다. 변경 전 생성한 표시 데이터는 그대로 두고 변경 후 새 표시 데이터를 만들어 최신 값이 나타나는지 확인한다.
- [ ] 손패/실행선의 변경 직후 갱신을 확인한다. 화면 판단이 필요한 것은 사용자가 Play에서 확인한다.
- [ ] 카드 상태 그리드·툴팁의 기존 미완료 작업 F4 전체를 이 작업에 흡수하지 않는다. 이번 변경을 표시하는 필수 접점만 해당 계획과 맞춘다.

**완료 조건:** 단계 B·C 각각이 이 절의 관련 검증을 통과한다. 기능을 끝낸 뒤 설명을 별도 후속 작업으로 남기지 않는다.

### 8. 단계 E — 상태 이름 중복 제거 (P2)

**변경 영역:** `StatusDescriptionRegistry`, `KoreanDescriptionCatalog`, `DescriptionContext`, 효과 설명·타임라인 포매터·설명 카탈로그 검증과 관련 테스트.

- [ ] 기존 이름·설명·로그의 기대 결과 테스트를 유지한다.
- [ ] 상태 이름 조회를 원본 콘텐츠 조회로 바꾸고 이름 복사·별도 등록을 제거한다.
- [ ] 미등록 상태·빈 이름에 대한 콘텐츠 검증을 유지한다. 단지 레지스트리 삭제 때문에 잘못된 콘텐츠가 통과하게 만들지 않는다.
- [ ] 제거로 고아가 된 코드만 정리한다. `IDescriptionGrammar` 등 다른 추상화 정리는 포함하지 않는다.
- [ ] `Tools/verify.sh` 전체 통과 후 별도 정리 커밋을 만든다.

**완료 조건:** 상태 이름의 별도 사본 없이 설명·로그가 기존과 같은 이름을 표시한다.

### 9. 실행과 검증 규칙

- 제품 코드는 전용 워크트리에서 수정한다. 메인 체크아웃의 브랜치를 전환하거나 `Assets/`를 수정하지 않는다.
- 각 구현 단계는 실패 테스트 확인 → 최소 구현 → 관련 헤드리스 검증 → 전체 검증 → 한국어 커밋 순서로 수행한다.
- 변경이 없는 기존 콘텐츠는 기존 전투·설명 테스트로 결과 불변을 확인한다. 새 밸런스 콘텐츠는 이 계획에 포함하지 않는다.
- 원본 공유 카드 격리, 전투 경계, 런 경계, 해결 중 변경, 효과 ID 참조를 단계별 리뷰에서 확인한다.
- 검증 명령은 [commands.md](../../agents/commands.md)의 `Tools/verify.sh`를 사용한다. master 머지는 별도 사용자 승인 후에만 한다.
- 구현 단계 종료 시 색인과 관련 백로그의 상태를 함께 갱신한다. 완료된 구현 계획은 규칙에 따라 보관한다.
