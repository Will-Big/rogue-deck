상세 작업·인터페이스·실패 테스트 · 승인된 구조 설계

무엇을 만드나

효과마다 위치를 다시 선택하고 직접 반응을 해결하며, 카드 종료에 승패를 판정하는 구조로 전환한다. 카드 시작 조건과 소비 결과 의존을 분리하고, 상태 만료는 공통 턴 시점으로 표현한다.

기존 효과 처리기·등록 구조를 유지한다. 코드에 여러 계약을 오래 공존시키기보다, 데이터 변경과 도구 왕복을 같은 작업에서 전환한다.

각 작업은 실패 테스트, 구현, 검증, 커밋 순서로 수행한다. T2a와 T2b는 커밋을 나누되 함께 끝낸다. 그 사이에는 편집 도구가 새 형식 카드를 읽기 전용으로 띄우므로 이 상태로 머지하지 않는다.

의존 방향

새 중앙 관리자로 모든 규칙을 모으지 않는다. 카드 실행기는 효과 진행을, 효과 실행기는 대상·사망·직접 반응의 경계를 연결한다. 계산은 등록된 개별 처리기에 남긴다.

확장 축

효과·조건·사건·반응 능력·위치 선택은 키와 처리기 등록으로 확장한다. 피해 보정과 방어 흡수는 반응 연쇄가 아니므로 그대로 적용한다. 반응 공격은 반응 공격을 부르지 않고, 사망 시 반응(전염)은 사망 원인과 무관하게 발동한다.

고정 계약은 효과 순차 처리, 반응 공격의 연쇄 금지, 카드 종료 승패, 패배 우선이다. 수명 정책은 공통 단계 방문으로 만료하며 방어 이름을 검사하지 않는다. 전역 관찰자 순서와 다중 대상 정량 지불은 이번 수용 범위 밖이다.

대안과 기각 이유

채택: 계약별 검증 후 전환

회귀 원인을 작업 단위로 좁히고 변경 책임을 검토할 수 있다.

기각: 한 번에 전체 교체

데이터·순서·반응·표시의 실패가 겹쳐 규칙 변경과 구현 오류를 구분하기 어렵다.

이 선택으로 어려워지는 것

  • T2a·T2b는 정의·카드 JSON 29장·설명·편집 도구를 함께 바꾼다. 변환 규칙으로 결정되지 않는 카드가 나오면 멈춘다(기준 시점에는 없음).
  • 치명타 버티기가 사라지므로, 다시 도입할 때 새 방식의 설계부터 시작해야 한다. 지금의 캐릭터 데이터·이벤트·로그 문구가 남지 않는다.
  • Unity 배치 검증이 단계마다 붙어 작업 시간이 는다. 라이선싱 장애가 나면 그 단계에서 멈출 수 있다.
  • 순서 의미가 바뀌므로 기존 테스트 기대값 중 일부를 교체해야 한다. 단순 기대값 변경이 아니라 승인된 사례로 변경 이유를 연결한다.
  • 별도 다중 적 작업과 세션 파일이 겹칠 수 있다. 최신 정책 호출부는 보존하고 본 계획의 턴 경계만 연결한다.
  • 스키마 테스트가 파일을 갱신할 수 있어 생성물도 검토하고 재검증해야 한다.

실행 예시

가상 카드: 피해 3 → 자신 방어 3 → 피해 3. 아군 HP 10, 적 HP 8, 적의 반격은 피해 2.

설계의 검증 사례 V01~V22를 각 작업에 대응시켰다. 직접 반응의 사망 능력, 방어 획득 반응, 사망 후 현재 카드의 계속 수행도 별도 테스트로 포함한다.

인계 기준

구현 담당자는 별도 요청 후 워크트리를 만들고 현재 코드를 다시 확인한다. 단계별 헤드리스 테스트, 데이터 전환 시 도구 왕복, 최종 전체 검증을 수행한다. 의미가 모호한 데이터나 승인 설계와 충돌하는 규칙은 임의로 고치지 않는다.

이 계획에는 향후 추가할 API와 테스트 코드가 포함되어 있지만 아직 실행하거나 소스 파일로 작성하지 않았다. 구현 시작은 별도 사용자 요청으로 결정한다.
