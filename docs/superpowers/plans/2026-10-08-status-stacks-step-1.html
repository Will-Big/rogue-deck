이번 단계의 목표와 범위

  • 목표: 개인 상태의 count와 중앙 규칙의 정도를 어디에 보관하고 누가 해석하는지 정한다.
  • 현재는 설계 검토다. 합산 API, 만료 정책 이행, 이벤트 스키마 등의 세부 구현은 각각 후속 단계에서 작성한다.
  • 확정된 사용자 요구: 구현 필드 Stacks 하나, 같은 상태 수치 합산, VisitsLeft 제거, 독립 기간 없음. 이 요구를 다시 후보로 올리지 않는다.

수치 해석

상태 종류인스턴스의 count → 코드 Stacks중앙 규칙의 값실행 의미
둔화·가속남은 턴실행 순서 변화 정도count가 늘어도 변화 정도는 커지지 않음
방어남은 방어량방어 관련 공통 규칙피해 흡수로 차감, 정해진 시점에 제거
독현재 독량성장량·피해 관련 규칙count를 피해량으로 사용하고 성장
소모형남은 사용 횟수해당 효과의 규칙성공적인 소모 때 감소
존재형 효과누적 수치존재 여부에 따른 규칙합산은 가능하나 효과를 count번 반복하지 않음

위 표는 제안 계약이다. 상태별 실제 이행·검증은 1.2와 1.3에서 정한다. 수치 0인 상태의 신규 적용과 제거 경계도 해당 단계에서 검토한다.

책임 분배 후보 — 추천 순서

순위구조 후보장점단점
1공통 StatusInstance + 기존 등록형 상태 행동현재 키 조회와 행동 구조 재사용, 단일 Stacks 요구에 직접 대응기존 두 수치를 읽던 경로의 이행 필요
2공통 StatusInstance + 별도 처리 정책 객체반복되는 감소·제거 정책 재사용정책 객체와 참조가 늘어남. 실제 반복이 확인돼야 이득
3상태별 StatusInstance 하위 클래스상태별 수치 의미가 타입에 드러남상태별 행동 계층과 역할이 겹치고 인스턴스 종류가 늘어남
  • 추천: 후보 1. 공통 수명 처리의 재사용은 유지하고, 정책 객체를 추가 추출할지는 1.3에서 판단한다.
  • JSON에는 이름·기본 수치·처리 시점 같은 저작 데이터를 둔다. 중첩 횟수에 따른 실행 알고리즘은 상태 행동이 담당한다.

실행 예시 — 둔화 수치와 정도의 구분

  1. 중앙 규칙에 둔화의 실행 순서 변화 정도 +2가 있다.
  2. A의 StatusBag은 둔화 인스턴스 하나를 보관한다. 현재 count는 3이며 코드 필드로는 Stacks = 3이다.
  3. 둔화 3을 추가로 받으면 같은 인스턴스의 Stacks는 6이 된다. 이 단계에서는 저장 위치와 결과만 확정하며 적용 메서드는 1.2에서 설계한다.
  4. 실행 순서 계산 경계는 StatusRegistry로 둔화 행동을 조회한다. 둔화 행동은 중앙 정도 +2를 사용한다. Stacks 6을 +6 또는 6회 실행으로 해석하지 않는다.
  5. 기간 감소 경계에서는 Stacks가 5가 된다. 어떤 시점에 감소하는지는 1.3에서 현재 처리 경로와 비교한다.
  6. 심볼 숫자는 5다. 호버 후보 문구는 “이 대상의 실행 카드 순서가 +2 됩니다. 둔화 수치는 매 턴 1 감소합니다.”이며 현재 count를 넣지 않는다. 설명 연결은 2.4에서 다룬다.

이번 단계의 검토 항목

  • □ 후보 1의 데이터/행동 분리와 객체별 책임이 적절한지 검토한다.
  • □ 단일 Stacks의 상태별 의미가 위 표와 일치하는지 검토한다.
  • □ 검토 결과를 반영한 뒤 1.1에 필요한 구현 계획을 작성한다. 구현 전에 이행 범위와 검증 항목을 구체화한다.
  • 다음 상세 작성 대상: 1.2 같은 상태의 합산 적용. 나머지 단계 상세는 아직 작성하지 않는다.
