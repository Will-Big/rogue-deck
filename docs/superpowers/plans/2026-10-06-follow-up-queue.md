# Fate Weaver — 후속 작업 상세

- 작성일: 2026-10-06
- 문서 유형: `active-roadmap`
- 상태: `active`
- 역할: [중앙 색인](../README.md) 「후속 작업 대기열」 표의 **상세**를 담는다. 색인에는 번호·한 줄 요약·

## 쓰는 법

- **번호(F1, F2 …)는 영구 ID다.** 재사용하지 않고, 끝난 항목은 색인 표와 이 문서에서 **함께 지운다**
  (번호는 결번으로 남는다). 구현 기록은 해당 스펙과 git 이력에 남긴다.
- 항목을 더할 때는 **같은 커밋에서** 색인 표에 행을 더한다.
- 상세가 다른 문서에 이미 있는 항목(F4·F5·F10·F13)은 여기에 본문을 두지 않는다. 색인 표가 그 문서를
  직접 가리킨다.
- 분류는 색인 표와 같다: `요구사항`(설계부터) · `진행 중` · `바로 가능` · `눈으로 확인`(규칙 17, 사용자 몫) ·
  `결정 필요` · `조건부`(조건이 찰 때).

## F1. 적 개체별 수치 변주 — `요구사항`

**전투 진입 시 적 개체별 기준 수치에 변주를 확정한다 — 2026-09-20 사용자 요구사항.**

같은 몬스터라도 개체마다 HP와 사용하는 카드의 피해 수치가 조금씩 다르도록 한다. 원본 몬스터·카드
콘텐츠에는 기준값만 두고, 전투 진입 시 적 인스턴스를 생성할 때 개체별 수치를 결정해 보관한다.
이 변주값은 전투 내내 유지하며 턴마다 또는 카드 실행마다 다시 추첨하지 않는다. 같은 카드 정의를
사용하는 다른 적에게 변주가 전파되지 않도록 원본과 개체별 값을 분리한다.
변동 폭은 `max(1, ceil(기준값 × 0.1))`로 확정한다(2026-09-20 사용자 추가 결정).
기준값의 10%를 먼저 올림한 정수 폭을 기준값에서 빼고 더해 양 끝을 포함한 정수 범위를 만든다.
따라서 올림 때문에 실제 변동률은 10%를 넘을 수 있으며, 엄격한 10% 상한은 적용하지 않는다.
예시: HP 30 → 27~33, HP 22 → 19~25, 카드 피해 8 → 7~9, 카드 피해 6 → 5~7.
낮은 기준값에서의 결과 하한, 수치별 추첨 분포·상관관계와 변주 대상의 상세 범위는
구현 전 설계에서 확정한다. 시드 기반 결정론을 유지하도록 설계한다.
스테이지 맵 생성 때는 노드의 적 편성을 확정하고, 전투 진입 때는 그 편성에 속한 적들의 개체별
실수치를 확정하는 두 시점을 구분한다. 의도는 같은 종류의 적 사이에도 차이를 주어 우선 공격 대상의
판단 여지를 만들고 반복 전투의 단조로움을 줄이는 것이다. 현재 적 생성은 정의의 최대 HP를 그대로
전달한다(`Assets/Core/Simulation/Run/ContentEncounterSource.cs:39`). 이 항목은 후속 요구사항 기록이며
지금의 구현 변경 지시는 아니다.

## F2. 스테이지 맵 생성 시 노드 내용 사전 확정 — `요구사항`

**스테이지 맵 생성 시 노드 내용을 미리 확정한다 — 2026-09-20 사용자 요구사항.**

런 시작 후 해당 스테이지의 맵과 노드들을 표시하기 전에 각 노드의 내용을 결정해 보관한다.
스테이지별로 등장 가능한 적 편성 풀과 이벤트 풀을 따로 구성한다. 전투 노드에는 특정 적 편성을,
이벤트 노드에는 특정 이벤트를 배정한다. 시드 기반 추첨을 사용한다면 맵 생성 시 수행하며,
노드 진입 시에는 다시 추첨하지 않고 이미 배정된 내용을 실행한다.
현재는 `CombatNode.Begin`에서 편성을 추첨한다
(`Assets/Core/Simulation/Run/CombatNode.cs:83`, `Assets/Core/Simulation/Run/ContentEncounterSource.cs:23`).
맵·스테이지 구현 시 이 선택 책임을 맵 생성 단계로 옮긴다. 내부 내용 확정과 맵에서의 정보 공개는
별개이며, 공개 범위는 추후 설계한다. 이 항목은 후속 요구사항 기록이고 지금의 구현 변경 지시는 아니다.

## F3. 보상용 캐릭터 풀의 임시 데이터 교체 — `진행 중`

[전투 노드 한 사이클](../specs/2026-09-15-combat-node-cycle-design.md)은
보상을 "살아남은 캐릭터 → 각자의 풀 → 카드"로 구현하지만, 캐릭터가 아직 설계되지 않아 `member_a`·`member_b`
모두 `starter` 풀을 가리키는 **임시 데이터**다. 캐릭터를 설계하면 캐릭터 JSON의 `pool`만 바꾸고(코드 변경 없음),
그때 "카드는 정확히 한 풀에만"(카드풀 설계 §1) 검증을 켠다. 같은 시드의 보상 결과는 이때 바뀐다.

**2026-10-06 진행 상황: 선행인 캐릭터 설계를 시작했다.** 기본 캐릭터 다섯 명을 캐릭터당 11장
(시작 7 + 추가 획득 4)으로 설계하는 중이며, 지금까지 정한 설계 원칙·검수한 상태와 효과 후보·선봉
카드 초안은 [상태·효과 후보 메모](<../../../Tools/card-idea-notebook/상태·효과 후보.md>)에 있다.
강한 컨셉이 확정된 것은 선봉의 요새화뿐이고, 나머지 네 캐릭터의 컨셉은 후보를 종합한 뒤 정한다.
메모는 참고 자료이며 스펙이 아니다 — 캐릭터 구성이 굳으면 스펙을 새로 쓰고, 기본 카드를 카드 차별화
예외로 두는 결정에 맞춰 카드풀 설계 §2.5와 시작 덱 구성(§2.4, 무작위 10장 시작 덱 스펙)도 그때 개정한다.

**2026-10-07~08 진행 상황.** 아래는 결정만 적는다. 표·카드·근거는 전부 메모에 있다.

- **목적을 좁혔다.** 다섯 명은 후보를 골고루 나눠 담는 캐릭터가 아니라 **컨셉이 어우러지는지 판단하기
  위한 묶음**이다. 중심 컨셉 하나(**HP를 잃는 것**)를 다섯 명이 서로 다른 강도로 건드린다(메모 §6 원칙 15~18).
  위 문단의 "선봉의 요새화가 확정"은 철회됐다 — 선봉은 확정된 캐릭터가 아니다(메모 §7).
- **다섯 명(가칭):** 혈주·광전사(강), 대속자·수호자(중), 회귀자(약). 혈주·광전사의 풀은 한 번 재설계했고
  신규 카드 검수가 남았다. 나머지 셋은 재설계 대기다(메모 §9).
- **풀 크기.** 시작 7장은 풀에 넣지 않는다. 풀은 8장에서 출발하되 **장수 제약을 두지 않는다.** 늘어나는
  부담은 카드 종류·획득 방법·제거 방법의 다양함으로 상쇄하며, 획득·제거 방법은 사용자가 따로 설계한다
  (메모 §6 원칙 2). 배경: 보상은 생존 캐릭터의 풀 전체에서 매번 `rewardChoices`(3)장을 뽑고, 가진 카드도
  이전에 보인 카드도 빼지 않는다(`Assets/Core/Simulation/Run/CombatNode.cs:173-190`). 풀이 4장이면 혼자인
  동안 보상 한 번에 풀의 75%가 보인다.
- **카드 저작 원칙**(메모 §6 원칙 19~23): 컨셉에 매몰되지 않는다 · HP를 대가로 내는 카드는 기본적으로
  만들지 않는다 · 상태를 거는 카드는 "분노 1."처럼 적는다 · 강한 컨셉 카드는 비용 3 · 모든 캐릭터는 조작
  카드와 특색에 맞는 드로우 카드를 가진다.
- **표기 규약**(메모 §0): 부착 대상은 캐릭터·파티·실행선 카드·손패 카드 넷, 진영과 제약은 대상 조건으로
  분리, 상태가 붙는 곳과 발동해 건드리는 것이 다르면 작용 대상을 따로 적는다(메모 §5-1).
- 이 작업에서 **키워드를 시험하는 방법** 문제가 갈라져 나왔다 → F15.

## F6. 턴 재생: 효과가 실행 즉시 보이지 않는다 — `바로 가능`

순간이 아니라 모든 연출이 끝난 뒤에야 화면에 나온다. 방어뿐 아니라 다른 효과도 모두 **실행 즉시**

[턴 재생 계층](../specs/2026-08-30-turn-playback-design.md)이다.

## F9. 계획 3.5가 남긴 콘텐츠·구조 항목 셋 — `결정 필요`

코드는 준비돼 있고 결정만 남았다.

- (a) **복수 개입** — 카드 한 장에 개입 액션 여럿. `CardDefinition.InterventionAction`이 단수이고
(`Assets/Core/Cards/CardDefinition.cs:109`) 비용이 액션마다 차감되므로, 대상 묶기 규칙과 비용 귀속을
함께 설계해야 한다.
- (b) **`lock` 개입 카드와 `SwapExecutionOrderSpec.TargetSide`를 쓰는 카드가 없다** — 액션은 등록돼 있고
테스트도 덮지만 대응 콘텐츠가 없다. 기본 캐릭터 설계는 잠그기를 쓰지 않기로 했다(2026-10-06).
- (c) **`BattleScreenController`의 입력 처리** — 손패 클릭·존 클릭·손패 호버·턴 버튼 넷이 아직
컨트롤러에 있다(`OnHandClicked`·`OnZoneClicked`·`OnHandHovered`·`OnTurnButton`). 전투 화면 분해
설계 §4.1대로 백로그 P2(코어 이벤트 확충) 이후로 미룬다.

## F15. 키워드·상태·카드 아이디어를 빠르게 검증하는 환경 — `요구사항`

**F3에서 갈라져 나온 작업 — 2026-10-08 사용자 요구와 논의 결과.** 계획 문서는 아직 없다. 아래는 논의에서
정해진 것과 남은 것의 기록이며 구현 지시가 아니다.

**문제.** 키워드나 상태를 하나 디자인할 때마다 ① 본체에 없는 구조면 구조를 고치고 ② 그 위에 카드를
만들고 ③ 시험하는 삼중 작업이 생긴다. 아이디어는 아직 정제되지 않았고 전투의 진행 방식 자체를 건드리는
것이 계속 나올 것이므로, 이 반복을 키워드마다 치르면 효율이 나오지 않는다. 목적은 아이디어마다 **재미가
있는지 · 밸런스가 이상하지 않은지 · 다른 것과 어울리는지**를 빠르게 가리는 것이다.

**정해진 것**

1. **구조를 고치는 단위는 키워드가 아니라 "이음매"다.** 키워드는 수십 개지만 본체에 요구하는 새 능력의
   종류는 아홉 가지 안팎으로 모인다. 이음매 하나를 만들면 그 줄의 키워드가 전부 가벼운 추가가 된다.
   사용자가 이 종합에 동의했다. 아래 분류는 메모의 규칙 문장을 읽고 한 추정이며 코드로 검증하지 않았다.

   | 이음매 (본체에 필요한 능력) | 쓰는 키워드 |
   |---|---|
   | 어떤 일이 일어나면 반응한다 | 분노, 흡혈, 재생, 응혈, 돌격 태세, 지원 사격, 현상금, 죽음의 예고 |
   | 다음 턴의 자원을 바꾼다 | 영감, 통찰, 과부하, 비축 |
   | 피해 계산에 끼어든다 | 힘, 보호막, 불굴, 요새화 |
   | 피해가 향하는 곳을 바꾼다 | 희생, 결속 |
   | 실행선 카드의 행동을 바꾼다 | 혼란, 겁먹음, 예속, 빙결, 좁히기, 메아리, 되풀이, 모방, 마지막 한 수, 절취, 세탁 |
   | 카드가 더미 사이를 옮겨 다닌다 | 되감기, 보류, 순환, 정리, 선별 |
   | 카드의 수치를 바꾼다 | 수치 맞바꾸기, 흠집, 숙성 |
   | 비용을 다른 것으로 낸다 | 헌혈 |
   | 적의 카드 묶음을 바꾼다 | 말소 |

   일부는 이미 있다: 주는 피해를 고치는 훅(`Assets/Core/Status/IStatusBehavior.cs:52`), 반응 등록
   (`Assets/Core/Registries/CombatRegistries.cs:45-48`, 지금은 전염 하나). "카드의 수치를 바꾼다"와 상태
   수치·파티 범용 효과는 [카드·상태 변경 로드맵](2026-10-07-card-status-mutation-roadmap.md)이 다루는
   범위와 겹치므로, 이음매 설계는 그 문서와 맞춰야 한다.

2. **키워드와 상태는 단독으로 검증할 수 없다.** 검증 대상은 언제나 "카드가 든 덱이 전투를 치른 결과"다.
   아이디어 종류에 따라 바꾸는 것이 다르다.
   - 새 카드: 기준 덱에 그 카드를 넣은 것과 뺀 것을 비교한다.
   - 새 카드 키워드(소멸·흡수·보류 등): 이미 있는 카드 여러 장에 붙인 것과 안 붙인 것을 비교한다.
   - 새 상태·효과: 그 상태를 거는 **시험용 카드를 비용·수치의 격자로 기계적으로 만들어** 한 묶음으로
     돌리고, 결과의 모양(넓게 괜찮은가, 좁은 구간에서만 괜찮은가, 특정 짝과 함께일 때만 좋은가)을 본다.
     제대로 된 카드는 상태가 통과한 뒤에 디자인한다.

3. **재미는 전투 기록에서 뽑은 대리 지표로 본다.** 타격감·테마의 설득력 같은 비수치 요소는 제외한다.
   후보: 판단의 무게(잘하는 봇과 무작위 봇의 차이), 선택의 폭(최선에 가까운 플레이의 수), 카드의 존재감
   (손에 왔을 때 내는 비율), 연계의 이득(조합의 성과가 각자의 합보다 좋은가), 혼자서의 성립, 폭주, 전투
   길이와 분산, 수치가 올라가는 기울기, 한 방의 크기, 아슬아슬함, 역전, 준비가 터지는 순간, 답답한 턴의
   비율, 단조로움. 수치가 **얼마일 때 재미있는가**는 정할 수 없으므로, 사용자가 이미 플레이해 본 기존
   카드·전투의 수치를 기준점으로 삼아 비교한다.

4. **봇은 실력과 성향을 여럿 둔다.** 실력(무작위 · 한 턴 최선 · 몇 턴 앞 보기 · 끝까지 여러 번 돌려 보기)과
   성향(공격·방어 우선, 조작 선호, 특정 컨셉 밀어붙이기)을 나누고, 봇들 **사이의 차이**를 지표로 쓴다.
   성향 봇은 "의도한 컨셉이 작동하는가"를, 끝까지 돌려 보는 봇은 "의도하지 않은 것이 있는가"를 본다.

5. **화면은 통과한 것에만 만든다.** 시험은 Unity 없이 돈다.

6. **상태는 클래스로 직접 구현한다(2026-10-08 사용자 결정).** 반응형 키워드("어떤 일이 일어나면 → 무엇을
   한다")를 코드 없이 JSON으로 쓰게 하는 안은 기각했다. "일어나는 일"을 본체가 알리게 만드는 비용(이음매)은
   어느 방식이든 같고, JSON 방식이 덜어 주는 것은 원래 가벼운 상태 클래스 몇 줄뿐인데 그 대가로 해석기·
   문법·검증을 새로 만들어야 한다. 같은 모양의 상태 클래스가 반복해서 쌓이면 그때 다시 본다.

7. **별도 시뮬레이터를 만들지 않고 본체에서 시험한다(2026-10-08 사용자 확정).** 본체에 이음매를 만들고
   그 위에서 봇과 지표를 돌린다. 논의는 "실제 엔진 + 실험용 낱말" → "별도 시뮬레이터" → 이 결정으로 옮겨
   왔다. 별도 시뮬레이터의 근거는 "본체에 새 키워드를 끼울 자리가 없다"였는데, 이음매를 본체에 만들기로
   하면 그 근거가 사라지고 규칙이 한 벌이라는 이점만 남는다. 대가는 첫 결과가 늦어진다는 것이다 —
   이음매가 먼저 있어야 시험할 수 있다.


**본체에 필요해지는 것**

- 이음매. 키워드가 여럿 걸린 줄은 특정 키워드의 생존과 무관하게 필요하다. 키워드가 하나뿐인 줄(비용
  대체, 적 묶음 변경)은 요구가 확실해질 때 만든다.
- 스스로 플레이하는 봇과 지표를 돌리는 실행기. 지금은 사람이 쓴 대본만 돌릴 수 있고
  (`Assets/Core/Simulation/MultiTurnRunner.cs:25`) 명령줄 도구가 없다(`docs/agents/commands.md` 「CLI는 없다」).
- 시험용 카드를 게임 콘텐츠(`Assets/StreamingAssets/Content/`)와 분리해 읽는 길.
- 전투 세션이 효과·상태 등록 목록을 안에서 직접 만든다(`Assets/Core/Simulation/DeckCombatSession.cs:155-158`).
  시험용 상태를 끼우려면 이 목록을 바깥에서 받을 수 있어야 한다.
