## 상세

### 이번 단계의 목표와 범위

- 목표: 개인 상태의 count와 중앙 규칙의 정도를 어디에 보관하고 누가 해석하는지 정한다.
- 현재는 설계 검토다. 합산 API, 만료 정책 이행, 이벤트 스키마 등의 세부 구현은 각각 후속 단계에서 작성한다.
- 확정된 사용자 요구: 구현 필드 `Stacks` 하나, 같은 상태 수치 합산, VisitsLeft 제거, 독립 기간 없음. 이 요구를 다시 후보로 올리지 않는다.

### 추천안 — 기존 데이터와 행동 분리 유지

| 객체 | 제안하는 책임 | 보관·참조 관계 |
|---|---|---|
| StatusBag | 보유자의 상태 인스턴스 보관 | 키당 StatusInstance 하나 소유 |
| StatusInstance | 부착된 상태의 현재 count 보관 | Key·Stacks와 처리 정책 메타데이터. Count·Magnitude·VisitsLeft 제거 |
| 중앙 규칙 데이터 | 정도·성장량·배율 보관 | 개인 Stacks를 보관하지 않음. 기간별 변경 저장 설계는 2.1에서 검토 |
| StatusRegistry | 키에 맞는 행동 조회 | IStatusBehavior 참조를 보관 |
| StatusBehavior와 상태별 행동 | 상태 규칙 계산 | SlowBehavior 등이 상속. 인스턴스와 중앙 규칙을 읽어 수치 의미 해석 |
| 공통 수명 처리 | 시점에 따른 감소·제거 | 별도 남은 기간 카운터 없이 Stacks 감소 또는 상태 제거. 상세는 1.3에서 검토 |

- 관리자는 하나로 합치지 않는다. 가방은 보관, 레지스트리는 조회, 행동은 계산을 담당한다.
- 상태 인스턴스마다 ‘남은 턴’ 필드를 추가하지 않는다. 기간 상태의 Stacks 자체가 남은 기간이다.
- 처리 시점·처리 방식은 숫자와 다른 메타데이터다. 이를 인스턴스에서 참조할지 중앙 정책에서 조회할지는 1.3의 검토 범위다.

### 수치 해석

| 상태 종류 | 인스턴스의 count → 코드 Stacks | 중앙 규칙의 값 | 실행 의미 |
|---|---|---|---|
| 둔화·가속 | 남은 턴 | 실행 순서 변화 정도 | count가 늘어도 변화 정도는 커지지 않음 |
| 방어 | 남은 방어량 | 방어 관련 공통 규칙 | 피해 흡수로 차감, 정해진 시점에 제거 |
| 독 | 현재 독량 | 성장량·피해 관련 규칙 | count를 피해량으로 사용하고 성장 |
| 소모형 | 남은 사용 횟수 | 해당 효과의 규칙 | 성공적인 소모 때 감소 |
| 존재형 효과 | 누적 수치 | 존재 여부에 따른 규칙 | 합산은 가능하나 효과를 count번 반복하지 않음 |

위 표는 제안 계약이다. 상태별 실제 이행·검증은 1.2와 1.3에서 정한다. 수치 0인 상태의 신규 적용과 제거 경계도 해당 단계에서 검토한다.

### 책임 분배 후보 — 추천 순서

| 순위 | 구조 후보 | 장점 | 단점 |
|---|---|---|---|
| 1 | 공통 StatusInstance + 기존 등록형 상태 행동 | 현재 키 조회와 행동 구조 재사용, 단일 Stacks 요구에 직접 대응 | 기존 두 수치를 읽던 경로의 이행 필요 |
| 2 | 공통 StatusInstance + 별도 처리 정책 객체 | 반복되는 감소·제거 정책 재사용 | 정책 객체와 참조가 늘어남. 실제 반복이 확인돼야 이득 |
| 3 | 상태별 StatusInstance 하위 클래스 | 상태별 수치 의미가 타입에 드러남 | 상태별 행동 계층과 역할이 겹치고 인스턴스 종류가 늘어남 |

- 추천: 후보 1. 공통 수명 처리의 재사용은 유지하고, 정책 객체를 추가 추출할지는 1.3에서 판단한다.
- JSON에는 이름·기본 수치·처리 시점 같은 저작 데이터를 둔다. 중첩 횟수에 따른 실행 알고리즘은 상태 행동이 담당한다.

### 실행 예시 — 둔화 수치와 정도의 구분

1. 중앙 규칙에 둔화의 실행 순서 변화 정도 +2가 있다.
2. A의 StatusBag은 둔화 인스턴스 하나를 보관한다. 현재 count는 3이며 코드 필드로는 Stacks = 3이다.
3. 둔화 3을 추가로 받으면 같은 인스턴스의 Stacks는 6이 된다. 이 단계에서는 저장 위치와 결과만 확정하며 적용 메서드는 1.2에서 설계한다.
4. 실행 순서 계산 경계는 StatusRegistry로 둔화 행동을 조회한다. 둔화 행동은 중앙 정도 +2를 사용한다. Stacks 6을 +6 또는 6회 실행으로 해석하지 않는다.
5. 기간 감소 경계에서는 Stacks가 5가 된다. 어떤 시점에 감소하는지는 1.3에서 현재 처리 경로와 비교한다.
6. 심볼 숫자는 5다. 호버 후보 문구는 “이 대상의 실행 카드 순서가 +2 됩니다. 둔화 수치는 매 턴 1 감소합니다.”이며 현재 count를 넣지 않는다. 설명 연결은 2.4에서 다룬다.
