한국어·영어 현지화 구현 계획

승인한 설계를 전용 워크트리에서 단계별로 구현한다. 번역 문구와 설명 조립의 분리를 먼저 검증하며, 제품의 짧은 표현/서술형 선택은 아직 결정하지 않는다.

구조와 책임

Simulation은 설명 의미 요청을 생성한다(Unity·번역 문구를 모름). CSV는 문장 틀을 제공한다(게임 상태를 모름). Unity는 요청을 번역 문장으로 렌더링한다(효과 실행을 모름). 표시 바인딩은 현재 locale의 결과를 화면에 반영한다(게임 규칙을 모름).

의존 방향과 구현 순서

  1. 불변 키·인수 요청: 외부 데이터 변경으로 요청이 변하지 않는지 헤드리스 테스트.
  2. 효과·조건 요청: 기존 모든 카드와 성공값·소비량 보상·대상을 보존하는지 테스트.
  3. Localization 설치와 공식 CSV 가져오기: ko/en·ID 안정성·삭제·번역 누락 검사.
  4. Smart Strings 렌더: 동일 요청으로 짧은 문장과 서술형 테스트 템플릿을 각각 검증.
  5. 화면 배선: 열린 카드·툴팁·보상까지 갱신하고 전투 상태·RNG 불변 확인.
  6. 전체 검증과 사용자 Play 검수 인계. master 머지는 별도 승인.

확장 축

표현 변경은 CSV 템플릿 변경으로 검증한다. locale은 런타임 선택이며 요청 계약과 대상 의미는 고정한다.

대안과 기각 이유

추천 경로는 의미 요청 → Unity 렌더 → 화면이다. 대안인 효과 → 한국어/영어 핸들러 복제 → 화면은 새 효과마다 코드를 복제하므로 기각한다. 설명 전체를 Unity로 이동하는 경로는 의미 검증을 헤드리스에서 잃으므로 기각한다.

이 선택으로 나중에 어려워지는 것

기존 문자열 반환 호출자·테스트를 이행해야 한다. CSV 가져오기와 Addressables 빌드가 번역 변경에도 필요하며 복합 조건은 실제 언어 검수가 필요하다.

실행 예시

상태 부여(poison, 1) 요청을 CSV의 {status} {amount}.로 표시하면 독 1.이 된다. 테스트에서 같은 요청의 템플릿을 {status} {amount}을 부여합니다.로 교체하면 독 1을 부여합니다.가 된다. 게임 효과·의미 요청·UI 코드는 바꾸지 않는다.
