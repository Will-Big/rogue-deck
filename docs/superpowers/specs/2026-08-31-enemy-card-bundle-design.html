2판에서 바뀐 것: 조건부 선택이 들어오면서 IEnemyTurnPolicy의 계약이 바뀐다. 1판의 “시그니처 불변”은 더 이상 사실이 아니다.

무엇을 만드나

지금 적은 평평한 카드 카탈로그에서 매 턴 낱장을 무작위로 뽑는다. 뽑는 개수까지 무작위라, 저작자가 정하지 않은 카드 조합이 화면에 나타난다.

선택 단위를 낱장에서 묶음으로 바꾼다. 적은 묶음 여러 개를 가지고, 한 턴에 묶음 하나가 통째로 전개된다. 카드 한 장짜리도 묶음으로 만든다.

어느 묶음을 고르는지는 정책이 정한다. 기본 선택자 셋(무작위 · 비복원 · 정해진 순서) 위에, 조건이 맞으면 특정 묶음을 강제하는 각본을 덧씌울 수 있다. 둘은 합성이라 “무작위 + 조건”, “순서 + 조건” 같은 조합에 새 클래스가 필요 없다.

범위 밖: 적 콘텐츠의 JSON 저작(별도 단계), 다중 적, 묶음을 플레이어에게 보여주는 표현. 이 문서는 GoblinDeck이 C#으로 남아 있는 상태에서 선택 단위와 선택 방식만 바꾼다.

구조

객체책임 (한 줄)이 객체가 모르는 것
EnemyCardBundle 한 턴에 함께 전개될 카드들을 담는다 언제 선택되는지, 소유자, 존, 실행 순서
EnemyTurnContext 선택 시점에 읽을 수 있는 것을 한데 넘긴다 (턴 번호 · RNG · 전투 상태 · 주인 적) 무엇이 선택될지, 조건이 무엇을 볼지
IEnemyTurnPolicy 이번 턴 전개할 카드 목록을 답한다 계약 변경 카드의 효과, 존, 소유자, 실행 순서
RandomPickPolicy · ShuffleBagPolicy · SequencePolicy 묶음 목록에서 하나를 고른다 (각각 무작위 · 비복원 · 정해진 순서) 조건, 다른 정책, 묶음의 내용
ScriptedPolicy 조건이 맞는 첫 규칙의 묶음을 내고, 없으면 기본 정책에 넘긴다 조건의 내용, 묶음의 내용, 기본 정책의 고르는 법
IBundleCondition 구현체 + 레지스트리 맥락을 보고 지금 참인지 답한다 어느 묶음과 짝인지, 다른 조건, 규칙 순서
DeckCombatSession.BeginTurn 받은 카드 목록을 실행 인스턴스로 만들어 존에 올린다 어떤 정책이었는지, 왜 그 카드인지, 묶음의 존재

Enemy에 MaxHp를 더한다. 지금 Enemy는 Id·Hp·Statuses뿐이라 “체력 절반 이하” 같은 조건을 계산할 수 없다. Enemy(id, hp)가 MaxHp = hp로 채우게 하면 기존 생성 지점은 그대로 컴파일된다.

의존 방향

확장 축

런타임에 갈아끼울 수 있다한번 정하면 고정된다
기본 선택자 (무작위 / 비복원 / 정해진 순서) 한 턴에 묶음 하나
조건 규칙의 목록과 순서 조건은 선택 시점의 상태만 본다 — 이력은 상태로 적어야 읽힌다
새 조건 (클래스 1개 + 키 등록, ScriptedPolicy는 불변) 경계를 넘는 것은 카드 목록 — 묶음도 조건도 넘지 않는다
묶음의 구성·개수, 같은 묶음에 다른 정책 물리기 묶음은 플레이어에게 보이지 않는다
각본을 각본으로 감싸기 (ScriptedPolicy가 스스로 정책이다) 묶음 안 카드의 실행 순서는 카드 자신이 정한다

대안과 기각 이유

조건이 이벤트를 구독한다 — 기각

정책이 코어의 이벤트 타임라인을 구독해 “피해를 받았다”를 듣고 내부에 누적해 두는 안이다. 매 턴 상태를 다시 읽지 않아도 되고, 상태에 남지 않는 이력(“이번 턴에 세 번 맞았다”)까지 답할 수 있다. 그런데 얻는 것에 비해 잃는 것이 구조적이다.

그러면 상태에 없는 이력은? “이번 턴에 세 번 맞았다” 같은 조건은 현재 상태를 아무리 봐도 알 수 없다. 그때의 답은 구독이 아니라 그 사실을 상태에 적는 것이다 — 상태로 적히면 조건은 그대로 읽고, 재현도 보장된다. 적의 특성을 전부 상태이상·버프로 처리하기로 한 결정과 같은 방향이다.

순서와 조건을 한 클래스에 넣는다 — 기각

ScriptedPolicy 하나가 “각본”이라는 이름으로 순서와 조건을 다 담고, 순서는 턴이 N이면 조건으로 표현하는 안이다. 이름이 셋으로 끝난다. 그러나 둘은 평가 방식이 실제로 다르다 — 순서는 턴 번호로 진행하고, 조건은 상태를 보고 가로챈다. 한 상자에 넣으면 5턴짜리 각본이 규칙 다섯 줄이 되고, “무작위 + 조건”처럼 둘을 겹치는 조합을 표현할 자리가 없어진다. 이름 하나를 더 쓰고 합성으로 두는 편이 싸다.

묶음 정체성을 존까지 내보낸다 — 기각

ExecutionCardInstance에 묶음 id를 달아 존·이벤트·표현까지 흘리면 “이 3장은 한 세트”를 플레이어가 볼 수 있고, 묶음을 통째로 조작하는 개입 카드도 열린다. 그러나 묶음을 보여주지 않기로 했으므로 지금은 값이 없고, 비용은 세 겹(존·이벤트·표현)으로 든다. 코어의 출력이 이벤트뿐이라 화면이 알려면 이벤트 계약부터 넓어진다.

이 선택으로 나중에 어려워지는 것

  • 기존 정책 계약이 깨진다. CardsForTurn(턴, RNG)가 CardsForTurn(맥락)이 되므로 구현 셋과 호출부(9개 파일 15곳)가 모두 바뀐다. 묶음 전환으로 어차피 다시 쓸 파일들이라 추가분은 작지만, 1판에서 약속한 “계약 불변”은 더 이상 사실이 아니다.
  • 조건은 상태에 적힌 것만 볼 수 있다. 이력을 묻는 조건을 원할 때마다 그 이력을 먼저 상태로 만들어야 한다. 조건 하나 추가가 아니라 “무엇을 상태로 남길지” 결정이 선행한다.
  • 묶음 단위 개입 카드를 못 만든다. “이 묶음을 통째로 뒤로 민다” 같은 카드를 넣으려면 위에서 기각한 안을 그때 실행해야 한다 — 존·이벤트·표현에 묶음 id를 다시 얹는 일이다.
  • 묶음이 실행 순서를 강제하지 못한다. 묶음 안 카드들도 각자의 ExecutionOrder로 존에서 정렬되므로 “반드시 A 다음 B”를 묶음이 보장할 수 없고, 플레이어의 개입 카드가 그 사이를 가른다. 묶음은 함께 등장한다는 뜻이지 붙어서 실행된다는 뜻이 아니다. 다만 실행 순서가 같을 때는 존의 정렬이 안정적이라 묶음에 적은 순서가 유지된다.
  • “한 턴에 묶음 하나”는 매개변수가 아니라 계약이다. 두 묶음을 동시에 전개하고 싶어지면 정책에 인자를 더하는 것으로 안 되고, 이 문서의 전제를 다시 여는 일이 된다.
  • 플레이어는 세트를 읽을 수 없다. 묶음이 화면에 드러나지 않으므로, 묶음 안 카드끼리 시너지를 설계해도 플레이어는 그것이 한 세트라는 단서를 얻지 못한다.
  • 기존 전투의 시드 재현이 깨진다. 무작위 소비가 “개수 + 낱장”에서 “묶음 하나”로 바뀌므로 같은 시드라도 다른 전개가 나온다. 결정론 자체는 유지되지만(규칙 7) 과거 시드로 기록한 기대값은 무효다.

실행 예시 — 고블린이 체력 절반 아래로 떨어져 농성한다

고블린은 묶음 넷을 갖는다. 실행 순서는 찌르기 6, 약삭빠른 찌르기 3, 조잡한 방어 4다.

  • A = 찌르기 — 늦은 단타
  • B = 약삭빠른 찌르기 + 조잡한 방어 — 선공 후 방어
  • C = 약삭빠른 찌르기 + 찌르기 — 앞뒤로 벌린 2연타
  • D = 조잡한 방어 + 조잡한 방어 — 농성, 방어도 6

정책은 ScriptedPolicy(규칙: [(체력 절반 이하) → D], 기본: RandomPickPolicy([A,B,C]))다. 고블린 최대 체력은 28이므로 문턱은 14다.

  1. 3턴이 시작되고 고블린 체력은 20이다

    BeginTurn(3)이 존을 비우고 맥락을 만든다 — 턴 3, 전투 RNG, 전투 상태, 주인은 goblin.

  2. ScriptedPolicy가 첫 규칙에게 묻는다

    “체력 절반 이하가 지금 참이야?” 조건이 맥락에서 Hp 20, MaxHp 28을 읽어 거짓을 답한다. 규칙이 더 없으므로 기본 정책에 넘긴다.

  3. RandomPickPolicy가 A·B·C 중 하나를 고른다

    rng.Next(3)을 한 번 굴려 2 — 묶음 C다. RNG 소비는 턴당 한 번으로, 지금의 “개수 뽑기 1회 + 카드 뽑기 1~2회”보다 줄어든다.

  4. C의 카드 목록만 경계를 넘는다

    [약삭빠른 찌르기, 찌르기]. 세션은 이것이 C였는지, 조건이 걸렸었는지 모른다. 실행 인스턴스 둘이 만들어지고 존에서 3 → 6으로 정렬된다. 플레이어는 그 사이에 자기 카드를 끼워 넣을 수 있다.

  5. 플레이어가 이 턴에 9 피해를 넣어 고블린이 11이 된다

    턴이 해석되고 끝난다. TurnResolver는 묶음이라는 단어를 모른 채 지금과 같이 돈다.

  6. 4턴 — 같은 첫 규칙이 이번엔 참이다

    조건이 Hp 11 ≤ 14로 참을 답한다. ScriptedPolicy가 기본 정책을 부르지 않고 묶음 D를 낸다 — RandomPickPolicy는 이 턴에 RNG를 한 번도 굴리지 않는다.

  7. 조잡한 방어 둘이 같은 순서 4로 깔린다

    BlockBehavior가 재부여를 합산하므로 방어도가 3 + 3 = 6이 된다. 체력이 14 아래로 유지되는 한 고블린은 매 턴 D로 농성한다.

사용자 판단이 필요한 지점

1. 첫 조건을 무엇으로 열까. 위 예시는 “체력 절반 이하”를 썼다. 문턱을 비율로 둘지 (MaxHp 필요) 절대값으로 둘지, 그리고 함께 열 조건이 더 있는지 — “N턴마다”, “특정 상태를 갖고 있을 때” 같은 것 — 은 밸런스 판단이다.

2. 고블린이 조건을 쓸지. 묶음 A~D는 확정됐지만, 고블린이 지금부터 농성 규칙을 갖는지 아니면 RandomPickPolicy만으로 시작하고 조건은 다음 적에서 처음 쓸지는 정해지지 않았다. 조건 없이 시작해도 구조는 그대로다.
