무엇을 만드나

지금 적은 평평한 카드 카탈로그에서 매 턴 낱장을 무작위로 뽑는다. 뽑는 개수까지 무작위라, 저작자가 정하지 않은 카드 조합이 화면에 나타난다.

선택 단위를 낱장에서 묶음으로 바꾼다. 적은 묶음 여러 개를 가지고, 한 턴에 묶음 하나가 통째로 전개된다. 어느 묶음을 고르는지는 패턴이 정한다 — 몹은 무작위로, 보스는 정해진 순서로 같은 기계를 돌린다. 카드 한 장짜리도 묶음으로 만든다.

범위 밖: 적 콘텐츠의 JSON 저작(별도 단계), 다중 적, 묶음을 플레이어에게 보여주는 표현. 이 문서는 GoblinDeck이 C#으로 남아 있는 상태에서 선택 단위만 바꾼다.

구조

객체책임 (한 줄)이 객체가 모르는 것
EnemyCardBundle 한 턴에 함께 전개될 카드들을 담는다 언제 선택되는지, 소유자, 존, 실행 순서
IEnemyTurnPolicy 이번 턴 전개할 카드 목록을 답한다 계약 불변 카드의 효과, 존, 소유자, 실행 순서
RandomBundlePolicy 묶음 목록에서 하나를 무작위로 고른다 묶음의 내용, 지난 턴에 무엇이 나왔는지
ShuffleBagPolicy 묶음을 비복원으로 하나씩 내고 소진되면 다시 섞는다 묶음의 내용, 턴 번호
EnemyIntent 묶음을 정해진 순서로 하나씩 낸다 묶음의 내용, RNG
GoblinDeck 고블린의 묶음 목록과 기본 패턴을 제공한다 고르는 방식의 구현
DeckCombatSession.BeginTurn 받은 카드 목록을 실행 인스턴스로 만들어 존에 올린다 불변 어떤 패턴이었는지, 왜 그 카드인지, 묶음의 존재

정책 셋은 전부 “묶음 목록에서 하나를 고른다”는 한 문장으로 책임이 적힌다. 고르는 규칙만 다르므로 쪼갤 이유가 없다(규칙 30). EnemyIntent는 이름이 이미 “적의 의도 = 정해진 순서”를 뜻해 그대로 두지만, JSON 저작 때 kind 값과 1:1로 읽히게 할지는 아래에서 판단을 받는다.

의존 방향

확장 축

런타임에 갈아끼울 수 있다한번 정하면 고정된다
적이 쓰는 패턴 (무작위 / 비복원 / 정해진 순서) 한 턴에 묶음 하나
묶음의 구성과 개수, 묶음당 카드 수 경계를 넘는 것은 카드 목록 — 묶음은 넘지 않는다
같은 묶음 목록에 다른 패턴을 물리는 것 묶음은 플레이어에게 보이지 않는다
새 패턴 추가 (클래스 1개 + 등록) 묶음 안 카드의 실행 순서는 카드 자신이 정한다

대안과 기각 이유

묶음 정체성을 존까지 내보낸다 — 기각

ExecutionCardInstance에 묶음 id를 달아 존·이벤트·표현까지 흘리는 안이다. “이 3장은 한 세트”를 플레이어가 볼 수 있고, 훗날 묶음을 통째로 조작하는 개입 카드도 열린다. 그러나 묶음을 보여주지 않기로 했으므로 지금은 값이 없고, 값을 못 받는 대신 비용은 세 겹으로 든다.

패턴을 없애고 덱만 둔다 — 기각

적도 플레이어처럼 덱에서 뽑기만 하게 하고 IEnemyTurnPolicy를 지우는 안이다. 구조가 가장 단순해지고 “적대적인 유저” 픽션에도 맞는다. 그러나 보스의 정해진 순서를 표현할 수 없다. 덱은 “무엇이 들었나”를 말할 뿐 “3턴엔 반드시 이것”을 말하지 못한다. 선택 규칙이 적마다 달라야 한다는 요구가 곧 이 seam이 존재하는 이유다.

이 선택으로 나중에 어려워지는 것

  • 묶음 단위 개입 카드를 못 만든다. “이 묶음을 통째로 뒤로 민다” 같은 카드를 넣으려면 위에서 기각한 안을 그때 실행해야 한다 — 존·이벤트·표현에 묶음 id를 다시 얹는 일이다.
  • 묶음이 실행 순서를 강제하지 못한다. 묶음 안 카드들도 각자의 ExecutionOrder로 존에서 정렬되므로, “이 묶음은 반드시 A 다음 B”를 묶음이 보장할 수 없다. 카드에 적힌 순서값으로 저작해야 하고, 플레이어의 개입 카드가 그 사이를 가른다. 묶음은 함께 등장한다는 뜻이지 붙어서 실행된다는 뜻이 아니다.
  • “한 턴에 묶음 하나”는 매개변수가 아니라 계약이다. 두 묶음을 동시에 전개하고 싶어지면 패턴에 인자를 더하는 것으로 안 되고, 이 문서의 전제를 다시 여는 일이 된다.
  • 플레이어는 세트를 읽을 수 없다. 묶음이 화면에 드러나지 않으므로, 묶음 안 카드끼리 시너지를 설계해도 플레이어는 그것이 한 세트라는 단서를 얻지 못한다. 시너지는 카드 텍스트로 스스로 설명되어야 한다.
  • 기존 전투의 시드 재현이 깨진다. 무작위가 소비되는 방식이 “개수 + 낱장 뽑기”에서 “묶음 하나 고르기”로 바뀌므로, 같은 시드라도 이전과 다른 전개가 나온다. 결정론 자체는 유지되지만(규칙 7) 과거 시드로 기록한 기대값은 무효다.

실행 예시 — 고블린이 3턴에 묶음 B를 낸다

GoblinDeck이 묶음 셋을 들고 있고, 패턴은 RandomBundlePolicy다. 전투 RNG는 시드 7로 3턴째까지 진행된 상태다.

  • 묶음 A = [찌르기(실행순서 6)]
  • 묶음 B = [약삭빠른 찌르기(3), 조잡한 방어(4)]
  • 묶음 C = [찌르기(6), 찌르기(6)]

  1. BeginTurn(3)이 존을 비운다

    지난 턴의 실행 카드가 모두 사라진다. 지금과 같다.

  2. CardsForTurn(3, rng)를 부른다

    RandomBundlePolicy가 rng.Next(3)을 한 번 굴려 1을 얻는다 — 묶음 B다. RNG 소비는 턴당 한 번으로, 지금의 “개수 뽑기 1회 + 카드 뽑기 1~2회”보다 줄어든다.

  3. 묶음 B의 카드 목록만 돌려준다

    [약삭빠른 찌르기, 조잡한 방어]. 묶음 B라는 사실은 여기서 버려진다 — 세션은 이것이 어느 묶음이었는지 모른다.

  4. 세션이 실행 인스턴스 둘을 만든다

    InstanceId 7·8, OwnerId goblin, IsLocked 둘 다 false. 실행 순서는 고블린의 상태 가방을 통과해 정해지는데, 이 턴에 둔화·가속이 없으므로 카드에 적힌 3과 4 그대로다.

  5. 존에 올라가 플레이어 카드와 섞인다

    정렬 결과는 약삭빠른 찌르기(3) → 조잡한 방어(4)다. 플레이어가 실행 순서 3짜리 카드를 배치하거나 개입 카드로 순서를 틀면 두 카드 사이로 끼어들 수 있다. 묶음이었다는 사실은 아무것도 막지 않는다.

  6. 턴이 해석된다

    TurnResolver는 지금과 완전히 같게 돈다. 묶음이라는 단어가 코어에 등장하지 않는다.

사용자 판단이 필요한 지점

1. SelfLockPolicy를 지울까. 간수 삭제로 사용처가 0이 됐다. 새 설계에서 “잠긴 채 나오는 카드”는 카드의 StartsLocked로 저작하므로 쓰임이 없어 보이지만, 간수 전용은 아니라 남겨 뒀다.

2. EnemyIntent를 패턴 가족에 맞춰 개명할까. 지금 이름은 뜻이 맞지만, 나중에 JSON의 kind가 random·shuffle_bag· sequence로 갈릴 때 셋 중 하나만 이름이 어긋난다. 개명하면 테스트 12개 파일에서 생성자 이름 한 줄씩을 바꿔야 한다 — 기계적이지만 공짜는 아니다.

3. 고블린의 묶음을 어떻게 짤까. 위 예시의 A·B·C는 설명용으로 지어낸 것이다. 현재 카드 3장으로 묶음을 몇 개, 어떤 조합으로 만들지는 밸런스 판단이라 사람이 정해야 한다.
