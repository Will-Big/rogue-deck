효과·조작 JSON을 코어 모양으로 맞추고 페이로드를 중첩한다

2026-10-17 · 설계 승인됨 · 구현 대기 · 도메인: 카드 저작

효과 한 줄과 조작 액션의 JSON 이름·구조를 코어 레코드와 똑같이 만들고, 카드 형식 버전과 구형 변환을 없앤다. 그 과정에서 consume_status의 개수를 페이로드에서 공통 칸 EffectValue로 옮긴다. 세션 인계용 상세

무엇을 만드나

저작자는 이제 사람이 아니라 AI 세션이다. 그래서 JSON 이름을 사람이 읽기 좋은 이름(value, count, amount, kind)에서 코어 이름(effectValue, key)으로 통일하고, 종류 전용 값은 payload 객체로 묶는다. 카드는 항상 최신 형식 하나로만 저장한다.

  • P1. 효과의 세기 숫자("얼마나")는 공통 칸 EffectValue에 둔다. 페이로드에는 그 종류만 쓰는 선택값("무엇을, 어떤 식으로")만 둔다.
  • P2. 효과·조작 JSON의 이름과 구조는 EffectData·InterventionActionData·페이로드 레코드를 그대로 따른다.
  • P3. 카드 JSON은 형식 버전을 갖지 않는다. 형식이 바뀌면 같은 커밋에서 모든 카드를 고친다.

지금은 consume_status만 P1을 어긴다. 개수를 페이로드에 두어(ConsumeStatusSpec.cs:28) 조건 성공 수치와 scaleBy가 소비 개수에 닿지 않는다(EffectExecutor.cs:178-186, ConsumeStatusHandler.cs:33).

의존이 한 객체로 몰리지 않는다. 페이로드 스펙은 코어 페이로드 레코드마다 하나씩 둔다(거울 관계). 형식 버전을 확인하고 옛 형식을 올리던 CardFormatMigration은 없어진다.

의존 방향

숫자가 EffectValue를 지나야 조건 교체와 scaling이 적용된다. 페이로드는 실행기가 열지 않고 핸들러까지 그대로 전달된다. 조작 카드는 InterventionActionData(Key, 비용, Payload)로 같은 길을 가되, 공통 숫자 칸이 없어 실행기 단계가 없다.

확장 축

바뀌는 것: 새 효과·조작을 추가할 때 그 스펙과 (필요하면) 페이로드 스펙·코어 레코드를 더한다. JSON 모양은 레코드에서 정해진다.

고정되는 것: 효과 한 줄의 공통 필드 이름(key, id, targetFaction, effectValue, successEffectValue, skipOnBasic, requirement, scaling, payload), 조작의 key·payload, "세기 숫자는 effectValue" 원칙, "카드는 항상 최신 형식" 원칙.

범위 밖: 시작 조건의 kind는 남긴다. 이것은 코어 Key가 아니라 미리 정한 조건 이름(닫힌 enum)이고, switch 한 곳에서 코어 조건 객체로 바뀐다(EffectSpec.cs:21-41). 코어 Condition에는 대응할 Key가 없고, 닫힌 구조는 기존 결정이다(열린 카드 저작 설계 §4.1). 카드 수준 필드 이름도 그대로다.

대안과 기각 이유

기각: 형식 버전을 3으로 올리고 v2→v3 변환을 둔다. 저장소의 카드는 모두 이번에 고치므로 변환할 대상이 없다. 변환기는 로딩 경계 코드를 키우고, 옛 형식 예시를 테스트에 남겨 AI가 옛 형식을 참고하게 만든다. 옛 형식은 변환기 없이도 조용히 통과하지 못한다 — 옛 필드 이름은 MissingMemberHandling.Error(ContentJson.cs:38)가, kind는 컨버터의 key 필수 검사가 거부한다.

기각: 코어 페이로드 레코드로 JSON을 바로 읽는다. 클래스는 줄지만 코어 레코드가 JSON 형식과 검증을 떠안는다. 열린 카드 저작 설계 §4.1의 "스펙이 자기 파라미터를 검증하고 코어로 변환한다" 구조와 어긋난다.

기각: EffectValue를 기반 클래스 EffectSpec에 둔다. 숫자가 없는 효과(trigger_status)에도 필드가 생겨, 지금 MissingMemberHandling.Error가 하는 거부가 사라진다. 숫자가 있는 스펙 6개가 각자 선언한다.

이 선택으로 나중에 어려워지는 것

  • 형식이 바뀔 때마다 그 커밋에서 모든 카드를 함께 고쳐야 한다. 저장소 밖에서 만든 옛 형식 JSON은 읽을 수 없다(변환기 없음).
  • 이번에 콘텐츠 35장과 테스트를 한 번에 바꿔야 한다. 테스트 수정 후보는 25개 파일이고, 형식 버전·구형 변환을 검증하던 테스트 7개는 지운다.
  • 페이로드 스펙과 코어 페이로드 레코드가 쌍으로 늘어난다. 한쪽만 고치면 P2가 깨진다.
  • 숫자가 없는 효과에 successEffectValue·scaling을 적으면 여전히 조용히 무시된다(기반 클래스 필드라 거부되지 않음). 후속 과제로 남긴다.
  • 사용자 결정으로 새 테스트를 쓰지 않는다. 소비 개수에 성공 수치·scaling이 적용되는 새 동작은 테스트 없이 들어간다(AGENTS.md 규칙 12와 긴장).
  • 시작 조건에는 kind가 남아, 효과·조작(key)과 판별자 이름이 다르다.

실행 예시

응축 파열(condensed_burst), 적의 독이 2개인 상황.

{ "key": "consume_status", "id": "e0", "targetFaction": "Enemy", "effectValue": 3,
  "payload": { "key": "poison", "mode": "UpTo" } },
{ "key": "damage", "id": "e1", "targetFaction": "Enemy", "effectValue": 2,
  "scaling": { "sourceEffectId": "e0", "perConsumed": 2 } }
단계객체값
1스펙 컨버터"key": "consume_status" → ConsumeStatusSpec, payload → ConsumeStatusPayloadSpec
2ConsumeStatusSpec.Build()EffectData(consume_status, EffectValue=3), Payload=ConsumeStatusPayload(poison, UpTo)
3EffectExecutor조건 없음 → ctx.EffectValue = 3
4ConsumeStatusHandlerTake(available=2, 3, UpTo) → 2개 소비, ConsumedAmount = 2
5EffectExecutor (e1)2 + 2 × 2 = 6
6DamageHandler피해 6

지금과 결과가 같다. 다른 점은, 이 카드에 시작 조건과 "successEffectValue": 5를 붙이면 조건 성공 시 실제로 5개까지 소비한다는 것이다. 지금은 그 값이 조용히 버려진다.

조작 카드 엇갈림(crossover)은 "intervention": { "key": "swap_execution_order", "payload": { "requireAdjacent": true } }가 되고, SwapExecutionOrderPayload(TargetSide=null, RequireAdjacent=true)로 바뀐다. 동작은 같다.

검증과 승인 범위

Tools/verify.sh 전체 통과(부팅 로드가 전 카드를 검증)와 카드 그래프 도구의 unittest 통과로 확인한다. Unity 레이어는 스펙을 참조하지 않는다. 구현은 전용 워크트리에서 하고, master 머지는 별도 승인 대상이다.
