무엇을 만드나

지금 전투 화면은 승패가 나면 안내 문구 한 줄로 끝난다. 이 작업은 전투 노드 하나를 처음부터 끝까지 완성한다 — 전투를 치르고, 이기면 살아남은 캐릭터들의 풀에서 시드로 뽑힌 카드 세 장 중 하나를 골라 그 풀 주인의 덱에 넣고, 바뀐 덱으로 다음 전투를 시작한다. 지면 처음부터 다시 한다.

두 단계로 나눈다. 1단계는 흐름(시드·결과·보상·덱 반영·화면)을 만들고 적과 수치는 지금의 C#을 그대로 쓴다. 2단계는 적·편성·캐릭터 스탯·전투 규칙을 JSON 저작으로 옮기고 C# 원본을 지운다. 두 단계 모두 끝에서 머지할 수 있다.

의존이 모이는 곳: CombatNodeFlow가 코어의 CombatNode와 Unity 뷰 셋을 모두 참조한다. 조정자라서 의도적으로 모은 것이다 — 이 객체는 판단 없이 "누구를 언제 부르나"만 갖는다. 여기에 규칙 판단이 새로 붙기 시작하면 쪼갤 신호다.

줄어드는 객체: BattleScreenController에서 전투 구성 조립(파티 로드아웃·고블린·튜닝·시드)이 빠진다. 지금 책임은 "구성하고, 입력 전달하고, 그린다"로 '그리고'가 둘이다.

의존 방향

시드: 노드마다 스트림을 새로 파생한다

원칙: 같은 시드 + 같은 행동 → 같은 결과. 행동과 무관하게 결과를 고정하지 않는다. 그리고 저작은 "가능한 것들"만 담고, 이번에 무엇이 나올지는 시드가 정한다.

확장 축

대안과 기각 이유

1. 보상 시드 — 런 전체 보상 스트림(Slay the Spire) vs 노드 시드

2. 흐름을 어디에 두나 — 컨트롤러에 얹기 vs 분리

이 선택으로 나중에 어려워지는 것

  • 콘텐츠를 추가하면 같은 시드의 결과가 바뀐다. 보상 대상 카드 목록과 편성 후보 목록이 길이·순서째 RNG 입력이다. 시드는 콘텐츠 버전에 묶인다.
  • 보상 추첨 방식을 바꾸는 순간 기존 시드가 모두 무효가 된다. 쌍 목록 순서(파티 순서 → 카드 id), 이름표 상수, 해시 혼합식이 사실상 저장 형식처럼 굳는다.
  • 임시 풀 데이터 기간에는 "카드는 정확히 한 풀에만" 검증을 켤 수 없다. 두 캐릭터가 같은 starter 풀을 가리키기 때문이다. 캐릭터 설계로 풀을 나누는 순간 같은 시드의 보상도 바뀐다.
  • 기존 Run 뼈대의 노드 목록 계열이 지워진다. RunDefinition·RunNodeData·RunNodeRegistry·IRunNodeHandler 등 7개 타입. 노드 목록은 런이 아니라 맵의 범주로 정했으므로, 맵은 이 뼈대를 되살리지 않고 새로 설계해야 한다.
  • 편성에는 적을 한 마리만 저작할 수 있다. 기존 세션이 정책 하나만 받고, 적이 둘 이상이면 적 카드의 주인을 비운다. 다중 적과 같은 적 여럿은 반드시 할 후속 작업이다. 그 비용을 줄이려고 이번에 적 JSON id와 전투 안 id(goblin#0)를 분리하고 편성 공급자가 적마다 (적, 정책) 쌍을 돌려주게 한다 — 후속 작업은 세션과 편성 검증 한 줄로 좁혀진다.
  • HP가 전투 사이에 이어지지 않는다. 세션이 최대 HP만 받는다. 반드시 할 후속 작업이며 RunMember.Hp 자리는 이미 있다. 그 전에 "전투 중 HP 0이 됐지만 파티가 이긴 파티원"의 런 처리 규칙을 정해야 한다.
  • C#에서 JSON으로 옮기는 동안 고블린 테스트 6개 파일을 옮겨야 한다. 옮기기 전에 같은 시드 타임라인을 골든으로 잡아 동등성을 먼저 증명한다.

실행 예시

런 시드 1, 파티 member_a(덱 10장)·member_b(덱 6장), 첫 전투에서 이기고 첫 후보를 고른 뒤 다음 전투로 간다. 시드·후보 값은 흐름을 보이기 위한 가상값이다. 실제 값은 구현 후 골든 테스트가 고정한다.

  1. CombatNodeFlow.Start → NewRun

    • 콘텐츠 로드 성공 → RunState(runSeed=1, party=[member_a 25/25 · 10장, member_b 25/25 · 6장], NodesEntered=0)

  2. CombatNode.Begin(run, context)

    • run.EnterNode() → nodeIndex=0, NodesEntered=1
    • SeedDerivation.NodeSeed(1, 0) → nodeSeed=0x5A1C3E07
    • Stream(nodeSeed, Encounter) → 편성 공급자 Pick → [(goblin#0 · specId goblin · 28HP, RandomPickPolicy)]
    • Stream(nodeSeed, Combat) → DeckCombatSession(seed=0x1F9B20D4)
    • Flow → BattleScreenController.Bind(session)

  3. 플레이어가 싸운다 — 5턴째 승리, member_b는 3턴째 사망

    • 재생 완료 · session.IsComplete · Outcome=Win → Flow.OnCombatFinished

  4. CombatNode.Conclude()

    • rng = Random(Stream(nodeSeed, Reward)) · 생존자 [member_a] → member_a의 풀 starter → 쌍 22개 (카드, member_a)
    • 3회 뽑기: (riposte, member_a) · (hasten, member_a) · (distill, member_a) — 소유자는 풀에서 따라온다
    • Phase=Reward → Flow → RewardChoiceView.Show(후보 3, 소유자 이름)

    같은 런 시드로 3턴 만에 이겼어도 생존자가 member_a뿐이면 후보는 같다. member_b도 살아 있었다면 쌍이 44개(두 캐릭터가 임시로 같은 풀)가 되어 후보와 소유자가 달라질 수 있고, 한 카드를 뽑으면 그 카드의 다른 소유자 쌍은 지워져 카드가 겹치지 않는다.

  5. 플레이어가 첫 카드를 누른다 — CombatNode.Choose(0)

    • member_a.Cards: 10장 → 11장(riposte 추가) · member_b 불변 · Phase=Done
    • RewardChoiceView.ShowNextButton

  6. "다음 전투" → CombatNode.Begin(run, context)

    • nodeIndex=1 → nodeSeed=0xC37E9A12(0번과 무관) → 전투·보상 스트림도 새로
    • 로드아웃: member_a 25/25 · 11장, member_b 25/25 · 6장 (HP 인계 없음 — 사망자도 다시 최대 HP)

패배했다면 4단계에서 Phase=Defeated, RunOutcome=Defeat, 보상 없음 → CombatResultView의 "처음부터" → 새 RunState.

단계와 사용자 확인

단계끝났을 때사용자 몫
1 — 흐름승리→보상→덱 반영→다음 전투, 패배→처음부터가 돈다. 적·수치는 C# 그대로. 머지 가능.두 패널의 위치·크기·색 조정, Play로 한 사이클
2 — 구성 저작위 표의 JSON 넷이 원본이 되고 대체 대상 C#이 사라진다. 1단계와 똑같이 돈다.Play로 동일 동작 확인

범위 밖: 맵(노드 목록은 Map/ 범주로 따로 설계), 세이브, 새 게임마다 런 시드 새로 뽑기, HP 인계, 보스·엘리트·영입, 사망 파티원의 카드 처리(유산), 캐릭터별 실제 풀 저작(이번엔 임시로 두 캐릭터 모두 starter), 패널 등장 연출.
반드시 할 후속 작업(색인 기록): HP 인계, 다중 적(적마다 정책·카드 주인), 같은 적 여럿.

승인받을 것

  1. 위 구조와 두 단계 분할.
  2. 앞선 합의에서 바뀐 점 하나: 처음엔 전투 노드를 기존 IRunNodeHandler의 첫 구현으로 두려 했으나, "노드 목록은 맵의 범주"로 정한 뒤에는 그 뼈대를 해석할 호출자가 없다. 그래서 CombatNode를 독립 객체로 두고 노드 목록 계열 7개 타입을 지운다(프로덕션 참조 0).
