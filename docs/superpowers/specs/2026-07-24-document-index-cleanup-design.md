# Fate Weaver 문서 정리와 중앙 색인 설계

- 작성일: 2026-07-24
- 문서 유형: `documentation-governance`
- 주 도메인: `repository-documentation`
- 상태: 설계 승인, 정리 작업 계획 작성 전
- 범위: `docs/superpowers`의 현행 문서 선별, 완료 문서 보관, 폐기 문서 삭제, 중앙 색인과 관리 규칙

## 1. 목적

`docs/superpowers/specs`와 `docs/superpowers/plans`에 현재 규칙, 완료된 구현 절차, 미완성 초안이 함께
쌓여 있어 새 작업을 시작할 때 어떤 문서가 현재 기준인지 판단하기 어렵다. 현행 문서를 앞으로 다시
참조할 소수의 기준 문서로 줄이고, 완료된 구현 문서는 별도 보관하며, 승인되지 않았거나 완전히 대체된
문서는 제거한다.

문서 정리 이후에는 새로 만들 `docs/superpowers/README.md`를 중앙 진입점으로 사용한다. Git 이력은
파일 이동과 삭제 전 내용을 계속 보존한다.

## 2. 검토한 구조

### 2.1 채택: 현행 문서 최소화와 구조 보존형 보관

```text
docs/superpowers/
├── README.md
├── specs/
├── plans/
└── archive/
    ├── README.md
    ├── specs/
    └── plans/
```

기존 `specs`와 `plans`의 의미를 유지한 채 완료 문서만 `archive` 아래 같은 구조로 옮긴다. 기존 경로
형태가 보존되어 링크를 고치기 쉽고, 현행 문서와 역사 기록을 디렉터리 수준에서 구분할 수 있다.

### 2.2 기각: 현행 문서까지 도메인별 디렉터리로 재편

`combat`, `cards`, `ui`, `run` 등으로 나누면 탐색은 쉬워지지만 파일 경로가 모두 바뀌고 문서 간 상대
링크 수정 범위가 지나치게 커진다. 도메인 구분은 중앙 색인의 열과 문서 머리말로 해결한다.

### 2.3 기각: 파일을 그대로 두고 상태 메타데이터만 추가

이동 위험은 작지만 완료된 계획 40여 개가 계속 현행 계획과 같은 위치에 남는다. 현재 기준을 빠르게
찾는다는 정리 목적을 충족하지 못한다.

## 3. 문서 상태와 우선권

중앙 색인은 다음 상태만 사용한다.

| 상태 | 의미 | 중앙 색인 노출 |
|---|---|---|
| `current` | 현재 규칙 또는 현재 구조를 설명하는 권위 문서 | 예 |
| `active` | 아직 끝나지 않았으며 현재 기준으로 실행 가능한 계획 | 예 |
| `needs-redesign` | 필요한 영역이지만 기존 문서를 그대로 실행할 수 없음 | 문서 링크 없이 공백으로 기록 |
| `archived` | 완료된 설계·계획·구현 기록 | 별도 보관 색인에서만 노출 |

현행 문서끼리 충돌하면 더 최근 문서라는 이유만으로 자동 승리하지 않는다. 중앙 색인의 `권위 범위`와
문서 안의 명시적인 `대체 관계`를 따른다. 새 문서가 기존 결정을 바꾸면 기존 문서의 해당 절을 함께
갱신하거나 대체 관계를 기록한다.

## 5. 현행 문서의 정합성 수정

정리는 콘텐츠를 새로 설계하는 작업이 아니다. 다만 현행 문서가 이미 확정된 최신 규칙과 충돌하는
부분은 다음 범위에서만 고친다.

### 5.1 파티 기반 전투 설계

- 승인되지 않은 시그니처 적 WIP와 폐기할 외형 후보 문서 링크를 제거한다.
- 공용 카드가 존재한다는 설명을 제거하고 모든 카드가 정확히 한 캐릭터 소유라는 규칙으로 맞춘다.
- 미정 상태인 인계 규칙을 카드풀 설계 §4의 확정된 유산 규칙으로 대체하고 그 문서를 연결한다.
- 구현 계획 대기라는 오래된 상태를 현재 구현·설계 상태에 맞게 고친다.

### 5.2 아키텍처와 구현 완료 문서

- 코어, 전투 화면, 설명 레지스트리, 열린 카드 저작 문서의 오래된 `구현 계획 대기` 상태를 현재
  레퍼런스 상태로 고친다.
- 상세 구현 절차는 보관 문서로 이동하고, 현행 문서는 현재 구조와 불변식을 설명하는 역할만 가진다.
- 아키텍처 백로그의 완료 항목은 완료 상태를 유지하되 구현 기록 링크를 새 보관 경로로 고친다.

### 5.3 런 사이클 공백

기존 런 설계는 `재화 없음`, `사망 카드 인계 없음`, 예전 카드 소유 모델을 전제로 한다. 최신 유산
규칙과 함께 그대로 실행할 수 없으므로 현행 문서에서 제외한다. 중앙 색인에는 런 사이클을
`needs-redesign`으로 표시하고, 재설계 시 보관된 문서와 현재 카드풀 설계를 함께 참고하게 한다.

- 이동으로 깨지는 상대 링크는 현행 또는 보관 위치에 맞게 수정한다.

## 8. 중앙 색인

`docs/superpowers/README.md`는 다음 순서로 구성한다.

1. 문서를 읽는 방법과 상태 정의
2. 현재 권위 문서
   - 핵심 아키텍처
   - 전투·파티 규칙
   - 카드 저작·설명
   - 카드풀·콘텐츠
   - UX·표현
3. 활성 계획과 로드맵
4. `needs-redesign` 영역
5. 보관소 진입 링크
6. 문서 추가·완료·대체 시 갱신 절차

각 현행 문서 항목은 `문서`, `유형`, `도메인`, `상태`, `권위 범위`, `다음 사용 시점`을 가진다.
검색을 위한 자유 태그보다 권위 범위와 다음 사용 시점을 우선한다.

## 9. 관리 규칙

문서 정리 이후 다음 규칙을 적용한다.

1. 새 스펙·계획을 추가할 때 같은 커밋에서 중앙 색인에 등록한다.
2. 구현이 끝난 세부 계획과 구현 기록은 현행 `plans`에 계속 두지 않고 `archive/plans`로 옮긴다.
3. 대체된 설계는 역사적 구현 근거가 있으면 보관하고, 승인되지 않은 WIP는 삭제한다.
4. 현행 결정을 바꾸는 문서는 기존 권위 문서와 중앙 색인의 대체 관계를 함께 갱신한다.
5. 현행 디렉터리에는 `current` 또는 `active` 문서만 둔다.
6. 임시 브레인스토밍은 승인 전 별도 브랜치나 워크트리에서 관리하고 미완성 상태로 `master`에
   병합하지 않는다.

이 규칙은 중앙 색인에 기록하고 `AGENTS.md`의 작업 방식에 중앙 색인 동시 갱신 의무를 한 줄 추가해
후속 AI 작업에서도 적용되게 한다.

## 10. 이동과 링크 갱신 순서

1. 작업 시작 시 기존 스펙 25개와 이 관리 스펙 1개를 합친 `specs` 26개, `plans` 43개라는 기준
   집합을 확인한다.
2. 중앙 색인과 보관소 디렉터리를 만든다.
3. 보관 대상 57개를 `git mv`로 이동한다.
4. 폐기 대상 2개를 삭제한다.
5. 현행 문서의 상태·충돌 문구·관련 링크를 수정한다.
6. 보관 문서의 상대 링크와 상단 보관 표시를 수정한다.
7. 중앙 색인과 보관소 색인을 실제 결과에 맞춰 완성한다.
8. `AGENTS.md`에 문서 색인 갱신 규칙을 추가한다.

이동 중 예상하지 못한 새 문서나 중복 경로가 발견되면 임의로 분류하지 않고 작업을 중단해 기준 목록을
다시 검토한다.

## 11. 검증

문서 정리는 다음 항목을 모두 만족해야 한다.

- 현행 `specs`에는 기존 유지 대상 8개와 이 관리 스펙만 존재한다.
- 현행 `plans`에는 아키텍처 백로그 1개만 존재한다.
- `archive/specs`에는 15개, `archive/plans`에는 42개가 존재한다.
- 폐기 대상 2개는 작업 트리에 존재하지 않는다.
- 중앙 색인의 모든 현행 링크와 보관소 색인의 모든 링크가 실제 파일을 가리킨다.
- 저장소 Markdown의 로컬 `.md` 링크가 이동 때문에 깨지지 않는다.
- 현행 문서가 삭제된 WIP나 외형 후보 문서를 참조하지 않는다.
- 현행 파티 문서의 카드 소유권과 유산 규칙이 카드풀 문서와 충돌하지 않는다.
- `git diff --check`가 이번 변경 범위에서 통과한다.
- 병합 전 전체 헤드리스 테스트가 통과한다.

## 12. 범위 밖

- 코드, Unity 에셋, 씬, 프리팹 변경
- 보관 문서의 설계 내용을 현재 기준으로 다시 작성
- 런 사이클과 유산 경제의 재설계
- 카드·캐릭터의 개별 콘텐츠 설계
- 저장소 밖 자료의 수집이나 복원
