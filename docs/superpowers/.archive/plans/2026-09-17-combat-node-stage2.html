서명을 어떻게 저장하나 — 전문 픽스처 파일 vs 해시 상수

전문 텍스트 파일은 차이를 바로 보여 주지만 Assets/ 아래에 두면 Unity .meta가 필요하고 수백 줄이 diff에 섞인다. 해시 상수를 박고, 실패 메시지에 실측 서명 전문을 출력하는 쪽을 택했다 — 비교는 한 줄, 진단은 실패할 때만.

이 선택으로 나중에 어려워지는 것

  • 골든은 시드·콘텐츠 버전에 묶인다. 시작 덱·풀·고블린 수치를 나중에 일부러 바꾸면 이 테스트가 실패한다. 그때는 "의도한 변경"임을 커밋에 적고 골든을 새로 잡아야 한다 — 이관용 안전망이 콘텐츠 변경 비용이 된다.
  • 헤드리스가 어셈블리 경계를 잡지 못한다. 헤드리스 프로젝트가 Core·Simulation을 한 어셈블리로 컴파일하므로, 태스크마다 grep 검사로 대신하고 진짜 확인은 태스크 8의 Unity 배치에서야 된다. 그 사이의 경계 위반은 grep 규칙에 걸리지 않는 형태(완전 수식 이름 등)라면 늦게 드러난다.
  • .meta가 태스크 8까지 커밋되지 않는다. 1~7 사이의 커밋은 Unity로 열면 새 GUID를 만든다. 중간 커밋을 체리픽하거나 다른 워크트리에서 열면 GUID가 갈릴 수 있다 — 1단계와 같은 방식이라 이 브랜치를 통째로 머지할 때만 안전하다.
  • Unity 코드가 헤드리스로 검증되지 않는 채 태스크 6·7에서 고쳐진다. 컴파일 유지용 한두 줄이지만, 틀리면 태스크 8 배치에서 처음 드러난다.

실행 예시 — 태스크 5의 끝

  1. 편성 로더와 부팅 연결이 테스트를 통과한 상태

    • ContentBootstrap.Load → … 캐릭터 → 적 [goblin] → 편성 [goblin_single] → Succeeded

  2. GoblinParityTests.BeginNode()에서 한 줄 교체

    • new GoblinEncounterSource() → new ContentEncounterSource(content, CombatRegistries.EnemyPolicies())

  3. 서명 계산 (런 시드 20260917, 노드 0)

    • 편성 스트림 rng.Next(1)=0 → goblin#0 · 28HP · 새 RandomPickPolicy(JSON 묶음 4개)
    • 턴마다: 손패 id@소유자 → 운명력이 되는 실행 카드 배치 → 해석 이벤트 → … → outcome → 보상 후보
    • SHA-256 = 태스크 1의 골든과 같음 → PASS

    다르다면 골든을 고치지 않는다. 실패 메시지의 서명 전문을 태스크 1 시점 서명과 비교해 어디서 갈렸는지(묶음 순서? 카드 수치? 정책 인스턴스 공유?) 보고하고 멈춘다.

승인받을 것

  1. 아홉 태스크의 순서와 경계, 그리고 "골든은 태스크 1 이후 고치지 않는다"는 규칙.
  2. 서명을 해시 상수로 저장(전문 파일 대신).
  3. 새 파일의 .meta를 태스크 8 배치에서 한꺼번에 커밋(1단계와 같은 방식).
  4. 태스크 8 끝의 Play 확인은 사용자 몫이고, 머지는 승인 후.
