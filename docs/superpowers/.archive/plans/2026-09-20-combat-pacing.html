전투를 4~5턴으로

설계 전투 템포 개선을 실행하는 계획이다. 코드는 건드리지 않고 Assets/StreamingAssets/Content/의 JSON만 고친다. 과제마다 테스트를 먼저 쓰고, 통과시키고, 커밋한다.

실행 인계용 상세 Markdown · 전용 워크트리에서 작업 · 머지는 사용자 승인 후

과제 흐름

위 줄(1→2)과 아래 줄(3→4→5)은 서로 독립이라 순서를 바꿔도 된다. 6은 앞의 다섯이 끝나야 의미가 있다. 각 과제는 그 자체로 통과하는 트리를 남기므로, 중간에 멈춰도 저장소가 깨지지 않는다.

과제가 남기는 것

과제끝났을 때잠그는 테스트
1. 카드 5종베기·파고들기·내려찍기·방패 치기·버티기가 카탈로그에 있다. 아직 어느 덱에도 없다StrikerCardContentTests
2. striker 덱파티원 B가 픽스처 대신 직접 피해 6장을 들고 온다StrikerDeckDataTests 외 3
3. 상쇄 수치방어 한 장을 뚫고 2가 들어온다DefenseBalanceContentTests
4. 고블린쉬는 턴이 없고 묶음이 덱처럼 돈다GoblinBundleContentTests
5. 고블린 새끼짝 전투가 약체 둘이 된다GoblinRuntContentTests
6. 측정턴 수가 목표 범위에 들고 문서·색인이 실제와 맞는다CombatPacingTests

3과 4는 GoblinParityTests의 골든 서명을 각각 한 번씩 갱신한다. 그래서 4를 3 뒤에 둔다 — 한 커밋에서 두 번 고치면 무엇이 무엇을 바꿨는지 사라진다.

측정을 어떻게 하나

Compare는 무조작과 조작을 나란히 돌려 개입 카드의 효과를 보는 도구라 "몇 턴에 끝나는가"를 재지 못한다. 그래서 과제 6이 탐욕 스크립트를 둔다 — 매 턴 손패의 실행 카드를 비용이 큰 것부터 에너지가 다할 때까지 내고, 승리까지의 턴 수를 센다. 시드 셋으로 단독·짝을 각각 잰다.

경계는 넓게 잡는다(단독 3~6, 짝 3~7). 이것은 목표의 가드이지 정확한 값의 골든이 아니다 — 카드 한 장을 조정할 때마다 깨지면 아무도 쓰지 않게 된다. 목표에서 크게 벗어날 때만 걸리면 된다.

실측 턴 수가 목표를 벗어나면 조정 순서가 정해져 있다: 고블린 HP → 내려찍기 피해 → 방어 수치. 한 번에 하나만 바꾸고 다시 잰다. 짝 전투만 어긋나면 고블린 새끼 쪽 수치만 만진다.

실패할 만한 지점

  • 카드 JSON의 키 순서. 저장소 카드 전부가 바이트 단위 왕복 검증을 받는다. 키 하나만 자리가 달라도 실패하고, 실패 메시지가 파일 이름을 알려준다. 플레이어 카드와 적 카드는 키 구성이 다르다 — 적 카드에는 비용·등급·태그가 없다.
  • 골든 서명 갱신을 기계적으로 하는 것. 서명 전문을 읽고 카드 순서와 이벤트 종류가 그대로인지 확인한 뒤에 상수를 바꾼다. 이벤트 종류가 달라졌다면 수치 변경이 아닌 다른 일이 일어난 것이다.
  • toxic_reclaim의 방어만 3으로. 같은 파일에 독 효과의 count가 따로 있다. 둘을 혼동하면 독 아키타입이 조용히 약해진다.
  • 파고들기의 대상. 이 한 장만 뒷줄을 때린다. FrontOne으로 잘못 저작하면 테스트는 통과하지만 짝 전투에 선택이 사라진다 — 그래서 전투 결과로 잠그는 테스트를 따로 둔다.
  • Unity 배치에 -quit를 붙이는 것. 테스트를 돌리지 않고 종료 코드 0으로 끝나 통과로 오진한다. 결과 XML의 failed="0"을 직접 본다.

사람이 해야 하는 것

구현이 끝나도 화면과 감각은 확인되지 않는다(규칙 17). 머지 전에 사용자가 Play로 봐야 하는 것은 셋이다.

  • 적 둘이 나오는 전투의 레이아웃 — 검증된 적이 없다.
  • 새 카드 6장의 프레임과 자동 생성 설명이 읽히는지.
  • 실제로 루즈하지 않게 느껴지는지. 턴 수는 테스트가 재지만 체감은 재지 못한다.
