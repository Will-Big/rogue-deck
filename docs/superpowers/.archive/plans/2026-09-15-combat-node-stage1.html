승인할 것은 태스크 경계와 순서, 멈추는 지점이다. 구조 자체는 설계 문서에서 승인됐다. 각 태스크의 전체 코드·테스트·명령은 짝이 되는 .md에 있다.

무엇을 만드나

승인된 설계의 1단계를 10개 태스크로 나눠 전용 워크트리(feat/combat-node-stage1)에서 구현한다. 끝나면 전투에서 이기면 생존 캐릭터 풀 기반 보상을 고르고 그 카드를 들고 다음 전투로 가며, 지면 처음부터 다시 한다. 적과 수치는 아직 C#이다.

코어 7개 태스크를 먼저 끝내고(모두 Unity 없이 10초 검증), Unity 2개 태스크에서 화면을 붙인 뒤, 마지막 태스크에서 사용자 확인과 문서 정리를 한다.

태스크와 순서

#산출물검증지우는 것
1SeedDerivation — 노드 시드·목적별 스트림골든 값 6개(독립 계산으로 미리 박음)—
2RunState를 파티·시드·노드 순번만 남게RunStateTests 재작성노드 목록 계열 7개 타입 + 테스트 2개
3캐릭터 JSON pool 키(두 캐릭터 모두 starter, 임시 데이터)로더 오류 2종 + 저장소 캐릭터 풀 확인—
4RunSetup.NewRun — 콘텐츠에서 시작 파티덱 조립·정의 공유·순서ContentLoadouts와 그 테스트
5Enemy.SpecId, 편성 공급 인터페이스, GoblinEncounterSourceid 분리, 매번 새 인스턴스—
6CharacterPoolRewardSource — 생존 캐릭터 풀의 (카드, 소유자) 쌍순서·소유자·빈 입력—
7CombatNode — 시작·결말·보상·선택·건너뛰기15개: 싸운 방식 무관, 노드별로 다름, 손으로 굴린 스트림과 일치, 사망자 제외, 겹친 풀, 예외들—
8RewardChoiceView·CombatResultView + EditorCreateEditMode 5개 (Task 9에서 실행)—
9컨트롤러 Bind로 축소, CombatNodeFlow, 씬 빌더, 프리팹 둘, 씬 재생성씬 배선 테스트 + EditMode 전체 배치컨트롤러의 _party·구성 조립·상수 둘
10PLAYTEST.md 6항목, 설계·색인 상태, 계획 보관사용자 Play—

멈추는 지점

  • Task 10 Step 3 — 사용자 확인. 워크트리를 Unity로 열어 Play로 6항목을 본다. 두 패널의 위치·크기·색은 사용자가 조정한다(규칙 17).
  • Task 10 Step 5 — 머지 승인. 승인 전에는 master에 합치지 않는다(규칙 19). 머지 후 Unity를 돌린 워크트리는 지운다.
  • 계획 밖 판단이 필요할 때. 테스트의 전제(예: 적의 999 피해가 앞줄 파티원에게 먼저 닿는다)가 깨지면 구현을 비틀지 않고 보고한다. 시드 동작을 계획과 다르게 바꾸지 않는다.

대안과 기각 이유

코어를 먼저 끝내고 Unity를 나중에 붙인다 vs 태스크마다 화면까지 세로로 자른다

이 선택으로 나중에 어려워지는 것

  • Task 4~8 사이에 멈추면 Unity 프로젝트가 컴파일되지 않는 브랜치가 남는다. 헤드리스는 통과하므로 CI는 초록이지만, 그 상태로는 워크트리를 에디터로 열 수 없다. 중단해야 하면 Task 9까지 가거나 WIP로 기록한다.
  • 첫 Unity 배치가 워크트리에 Library/ 약 2.4GB를 만든다. 머지 후 워크트리를 반드시 지운다.
  • Unity 테스트는 Task 8에서 쓰고 Task 9에서 처음 돈다. 뷰 테스트가 실패하면 Task 9 안에서 고치게 되어 두 태스크의 경계가 흐려질 수 있다.
  • 시드 골든 값이 테스트에 박힌다. 파생식을 바꾸는 순간 이 테스트가 먼저 깨진다 — 의도한 잠금이지만, 바꿀 때마다 골든 값을 다시 계산해야 한다.

실행 예시 — Task 7의 테스트 하나

Dead_characters_are_never_owners가 계획대로 어떻게 도는지 따라간다.

  1. 준비

    • 파티: a(카드 0장, 앞줄) · b(hit 6장 — 피해 5, 비용 0)
    • 적: dummy#0, HP 5, 매 턴 smash(실행 순서 1, 피해 999)
    • 풀: a → a1..a6 · b → b1..b6 · 보상 3장 · 런 시드 11

  2. CombatNode.Begin

    • 편성 스트림 → 적 1마리 확인 → EnterNode() = 0 → 전투 스트림 시드로 세션

  3. 턴 0

    • b의 hit(순서 5)을 낸다 → 해석: smash(순서 1)가 앞줄 a를 쓰러뜨림 → hit가 적 HP 5를 0으로 → Win
    • 전제 단언: a는 죽었다

  4. Conclude()

    • 생존자 [b] → 쌍 6개 (b1..b6, 소유자 b) → 보상 스트림으로 3번 뽑고 뽑힌 카드의 쌍 제거
    • 단언: 후보 3장, 전부 소유자 b, 전부 b 풀의 카드

승인받을 것

  1. 10개 태스크의 경계와 순서, 두 멈춤 지점.
  2. Task 4~8 동안 Unity 컴파일이 깨져 있는 구간을 감수하는 것.
  3. 계획 작성 중 설계 상세에 맞춘 두 가지: Begin에서 적 수 검사를 노드 순번 증가 앞으로 옮김(시드 결과 동일), 보상 슬롯에 카드 대신 선택 버튼을 둠(버튼 문구는 에디터 빌더가 프리팹에 굽는 기존 관례).
